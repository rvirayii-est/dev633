## 2. Plain-English explanation
Lesson 25 *read* the shop's tables. Now you *design* them. A good schema makes wrong data impossible to store.

### Step 1: nouns and verbs
Read what the shop does and underline. **Nouns** become tables: *product, customer, sale, stock movement*. **Verbs** become relationships: a customer **makes** sales; a sale **contains** products (many-to-many, so `sale_line` in the middle); stock **moves** in and out of a product. Ask "one or many, required or optional?" in both directions. Sale-to-customer is optional (the walk-in).

### Step 2: keys
Every table gets a **primary key**. We use a **surrogate key**: a meaningless number the database hands out (`id`). The alternative is a **natural key** (the product name). Names change ("Rice 25kg" becomes "Rice 25 kg") and a changed key means changing every row that points at it. A number never needs to change. But the name must still be **unique**, so we say so with `UNIQUE`.

### Step 3: types
| Column holds | Use | Why not something else |
|---|---|---|
| Money | `DECIMAL(10,2)` | `DOUBLE` has the 0.1 + 0.2 problem (lesson 20). 10 digits, 2 after the point: up to 99,999,999.99 |
| Whole numbers | `INT` | |
| Names, phones | `VARCHAR(n)` | A phone is *text*: it has a leading 0 and no one adds phone numbers |
| Moment in time | `TIMESTAMP` | The shop's local clock, like `LocalDateTime` |
| Fixed choices | `VARCHAR` + `CHECK ... IN (...)` | Same words as the Java enums: `CASH`, `GCASH`, `CARD`, `RECEIVED`, `SOLD` |

### Step 4: constraints (rules the database enforces)
A **constraint** is a rule attached to a table. The database checks it on every `INSERT` and `UPDATE`, whichever program sends it: our app, a spreadsheet import, or a tired person typing SQL at midnight. It is the last line of defence, and Java's checks in `Product` are the first. The schema repeats the Java rules on purpose, and `SchemaRulesTest` has a test proving that both agree on which prices are allowed.

Always give constraints a **name** (`CONSTRAINT ck_product_price CHECK (...)`): the error message then says which rule broke.

| Constraint | Meaning | In the shop |
|---|---|---|
| `NOT NULL` | a value is required | every product has a name and a price |
| `UNIQUE` | no two rows share this value | product name; customer name **and** phone together |
| `CHECK (...)` | a condition must be true | price from 0.01 to 10000.00; quantity not negative; payment is a known method |
| `FOREIGN KEY` | must point at an existing row | a sale line's product exists |
| `DEFAULT` | the value if you give none | `quantity` starts at 0, `discount` at `'none'` |

### Step 5: what happens on delete?
A foreign key must also say what to do when the row it points at is deleted (`ON DELETE ...`). There is no universal answer; decide per link, by asking "what does the shop want?":

| Link | Choice | Reason |
|---|---|---|
| `sale_line.product_id` | `RESTRICT` (default): refuse | history must not point at a product that no longer exists |
| `sale.customer_id` | `SET NULL`: keep the sale, forget the link | the shop's income must not vanish with a contact; the sale becomes a walk-in |
| `sale_line.sale_id` | `CASCADE`: delete the children too | a line is meaningless without its sale |

```sql
-- shop schema
DELETE FROM product WHERE name = 'Rice 25kg';
```
```text
error 23503
```
```sql
-- shop schema
DELETE FROM customer WHERE name = 'Ana Reyes';
SELECT COUNT(*) AS sales_without_customer FROM sale WHERE customer_id IS NULL;
```
```text
sales_without_customer
----------------------
4
(1 row)
```
```sql
-- shop schema
DELETE FROM sale WHERE id = 3;
SELECT COUNT(*) AS lines_left FROM sale_line;
```
```text
lines_left
----------
6
(1 row)
```
`examples/DeleteRules.java` shows all three in one run. Be careful with `CASCADE`: one `DELETE` can remove many rows. In a real shop you would rather never delete sales at all (mark them cancelled).

### Step 6: normalization, in plain words
**Normalization** means arranging tables so that each fact is stored in one place. Three rules cover most of it:
1. **First normal form (1NF): one value per cell.** No lists inside a cell. A column `products = "Rice, Sugar"` makes counting and joining impossible. Give each product its own `sale_line` row.
2. **Second normal form (2NF): every column depends on the *whole* key.** In `sale_line (sale_id, product_id, product_name, quantity)` the `product_name` depends only on `product_id`, not on the pair. Move it to `product`.
3. **Third normal form (3NF): columns depend on the key and *nothing else*.** If `sale` held `customer_id` **and** `customer_phone`, the phone depends on the customer, not on the sale. Move it to `customer`.

A slogan to remember: *"every column depends on the key, the whole key, and nothing but the key."*

### Step 7: copying on purpose (denormalization)
A rule is a tool, not a law. This schema copies or compresses data in four places, each for a reason:
- `sale_line.unit_price` **copies** `product.price`. Prices change; a receipt from last week must not. (The Java `SaleLine` record makes the same choice: it copies the name and the price.)
- `product.quantity` can be **computed** from the stock log (RECEIVED minus SOLD) but is stored for speed. The audit query of lesson 27 proves the two agree. A stored copy needs a guard.
- `sale.discount` keeps the short text code (`none`, `percent:10`, `senior`) that `DiscountCodes` already reads and writes. A fully normalised design would have a `discount` table; the code is simpler and the Java class stays the single place that understands discounts.
- `customer.points` is **not** stored at all: it is worked out from the sales (as `DataStore` already did in lesson 19). Never store what you can compute unless you must.

### Step 8: indexes
An **index** is a sorted side-list that lets the database find rows without reading the whole table, like the index at the back of a book. The primary key and `UNIQUE` columns already have one. Add one to columns you often **search, join or sort by**. Each index makes reading faster and writing slightly slower and uses disk, so add them with a reason:
- `sale_line (sale_id)`: every receipt looks up its lines;
- `sale_line (product_id)`: "how many of this product did we sell?";
- `sale (sold_at)`: reports by day;
- `stock_movement (product_id, moved_at)`: the history of one product, newest first.

The indexes and constraint names are in the catalogue the database keeps about itself. Ask it:
```sql
-- shop schema
SELECT LOWER(constraint_name) AS rule FROM information_schema.table_constraints
WHERE LOWER(constraint_name) LIKE '%sale\_line%' ESCAPE '\'
ORDER BY 1;
```
```text
rule
---------------------
ck_sale_line_price
ck_sale_line_quantity
fk_sale_line_product
fk_sale_line_sale
(4 rows)
```

### What changes on PostgreSQL or MySQL?
| Thing | H2 (this course) | PostgreSQL | MySQL (8) |
|---|---|---|---|
| Self-numbered key | `INT GENERATED BY DEFAULT AS IDENTITY` | same (or `SERIAL`, older style) | `INT AUTO_INCREMENT` |
| Money | `DECIMAL(10,2)` | same | same |
| Time | `TIMESTAMP` | `TIMESTAMP` (or `TIMESTAMPTZ` with time zone, better for servers in several places) | `DATETIME` or `TIMESTAMP` |
| `CHECK` | enforced | enforced | enforced from 8.0.16; **silently ignored** before |
| `TRIM(name) <> ''` | works | works | works |
| Naming | names kept in capitals | folded to lower case | as written |
| `ON DELETE` | same words | same words | same words |
| Reserved words | `DAY`, `VALUE`, `USER` are reserved | different list | different list (`RANK`, `GROUPS`) |
| Index on `UNIQUE` | automatic | automatic | automatic |

Everything else in `schema.sql` is standard SQL and runs unchanged.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `Check constraint violation: "CK_PRODUCT_PRICE ..."` | A value broke the named rule. That is the rule doing its job | Fix the data; if the rule is wrong, change the schema (lesson 32) |
| `NULL not allowed for column "PRICE"` | A `NOT NULL` column got no value and has no `DEFAULT` | Supply the value |
| `Unique index or primary key violation` | Two rows with the same unique value | Look the row up first, or use the existing one |
| `Referential integrity constraint violation` on insert | The parent row does not exist yet | Insert the parent first |
| The same error on delete | Other rows still point at this one (`RESTRICT`) | Delete or move the children first, or choose another `ON DELETE` rule |
| `Table "SALE_LINE" not found` while creating `sale_line` | Tables must be created parent first: `sale_line` needs `sale` and `product` | Order the `CREATE TABLE`s: parents before children |
| A `CHECK` does not stop `NULL` | `NULL` makes the condition unknown, and an unknown passes a `CHECK` | Also say `NOT NULL` |
| `DROP TABLE` or re-running the script fails: "already exists" | The script is not repeatable | Start from an empty database (tests do), or use migrations (lesson 32) |
| Too many indexes | Each slows every `INSERT` | Add an index for a query you really run |

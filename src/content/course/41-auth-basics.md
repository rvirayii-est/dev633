## 1. Learning objectives
After this lesson you can:
- **explain** *authentication* ("who are you?") and *authorization* ("what may you do?"), and say when the answer is `401` and when it is `403`;
- **explain** why a database must never hold passwords, only *salted hashes*, and why you use BCrypt from a library instead of writing your own;
- **lock** the API with Spring Security so every endpoint except `/hello` needs a username and password (HTTP Basic);
- **store** users in a table created by a Flyway migration and let Spring Security read them;
- **test** a secured API with `MockMvc` (`httpBasic(...)`, `@WithMockUser`) and with a real HTTP client.

## 2. Plain-English explanation
Until now anyone who could reach the API could read the stock, change prices and delete products. A shop cannot run like that. Two questions must be answered on every request, in this order:

| Question | Name | Failure answer | This lesson? |
|---|---|---|---|
| **Who are you?** | *Authentication* | `401 Unauthorized` (we do not know you, or your password is wrong) | yes |
| **May you do this?** | *Authorization* | `403 Forbidden` (we know you; the answer is no) | lesson 42 |

(`401` is badly named: it really means "unauthenticated". Remember it as "I don't know you", and `403` as "I know you, and no".)

### Passwords: never store them
If a database is stolen, every stored password is stolen with it, and people reuse passwords. So the table keeps a **hash**: the result of a one-way scramble. You cannot turn a hash back into the password, but you can hash what someone types and compare the two.

A plain hash is still weak: two users with the same password get the same hash, and attackers keep tables of common passwords already hashed. Two fixes, both built into **BCrypt**:
- a **salt**: random bytes mixed in, so the same password gives a different hash every time (`thePasswordIsStoredAsABcryptHash...` and `theSamePasswordHashesDifferentlyEveryTime...` in `AuthenticationTest` show it);
- **slowness**: BCrypt is made to take a fraction of a second, which is nothing for one login and ruinous for someone trying billions of guesses.

A BCrypt hash is 60 characters and looks like `$2a$10$` followed by 53 characters (`$2a$` is the version, `10` the cost). **Never write your own hashing or encryption scheme.** Use the library; `PasswordHashing.java` (examples) only shows *why*, with Java's built-in PBKDF2.

### HTTP Basic: the simplest way to say who you are
With HTTP Basic the client sends this header on **every** request:
```text
Authorization: Basic YWRtaW46YWRtaW4xMjM=
```
The part after `Basic ` is `admin:admin123` in Base64. **Base64 is not encryption**: anyone who sees the header can read the password. So Basic is only safe over **HTTPS** (lesson 46 says where that comes from). `curl -u admin:admin123 ...` builds the header for you, and so does `httpBasic("admin", "admin123")` in a test.

Honest comparison with what you will meet at work:
- **HTTP Basic** (this lesson): trivial to build and to test, perfect for learning and for internal tools. Weaknesses: the password travels with every request, and there is no logout or expiry.
- **Tokens / JWT** (the usual next step for apps with a login screen): the client sends the password **once** to a login endpoint, gets back a signed, short-lived *token*, and sends the token afterwards. Spring Security supports this (an "OAuth2 resource server"), but you also need to decide how tokens expire, are refreshed and are revoked, and that is a lesson of its own. This course does not do it, and does not hand-roll it either: signing tokens is exactly the kind of crypto you take from a library or an identity service (Keycloak, Auth0, and so on).

### How Spring Security fits in
Spring Security is a **chain of filters**. Every request goes through the chain *before* it reaches a controller:
```text
request --> [ read the Authorization header ] --> [ is this user known? password right? ] --> [ is this URL allowed? ] --> controller
                      BasicAuthenticationFilter            UserDetailsService + PasswordEncoder           authorizeHttpRequests
```
Adding the dependency `spring-boot-starter-security` is enough to lock **everything**. We then tell it three things in `SecurityConfig`:
1. **who the users are**: `DbUserDetailsService` loads a row from the table `app_user`;
2. **how passwords are compared**: the `PasswordEncoder` bean is BCrypt;
3. **what is open**: `/hello` and `/error`; every other request must be authenticated.

Two more decisions you will see in the code, both with comments:
- **CSRF is switched off.** CSRF protects sites that keep you logged in with a *cookie*. This API is *stateless*: no session, no cookie, every request carries its own credentials, so there is nothing for a forged page to ride on. (A web page with a login form would keep CSRF on.)
- **Security errors use our own JSON.** The filter chain runs *before* the controllers, so the `ApiExceptionHandler` of lesson 39 never sees a refused request. `SecurityConfig` therefore writes the same `ErrorResponse` itself, and a client still reads one shape for every error.

## 5. Practical exercises
In `exercises/` (`AuthDrills.java`; tests in `Exercises41Test.java`): the small pieces behind the header, written by hand so there is no magic.
1. `basicHeader("admin", "admin123")` builds `Basic YWRtaW46YWRtaW4xMjM=`.
2. `parseBasicHeader(header)` reads it back (splitting at the **first** colon) and refuses `Bearer`, bad Base64 and a missing colon.
3. `passwordProblems(password)` lists what is wrong with a new password, in a fixed order.
4. `statusFor(sentCredentials, credentialsAreValid, allowed)`: `401`, `403` or `200`. The order of the checks is the point.
5. `mask(secret)` for logs: `a*******`.
6. `looksLikeBcrypt(text)`: recognise `$2a$10$...` with a regular expression.

*Stretch:* write `passwordProblems` so it also refuses the ten most common passwords from a list. (Real systems check against lists of leaked passwords, not just character rules.)

## 6. Expected results

```text
sha256(admin123) twice the same?  true
sha256 length: 64 hex characters, always the same for the same input
pbkdf2, two salts, same password: hashes equal?  false
right password matches?  true
wrong password matches?  false
Basic YWRtaW46YWRtaW4xMjM=
decoded by anyone: admin:admin123
```
With the app running (`java -jar .../shop-api.jar`):
```bash
curl -i localhost:8080/products
```
```text
HTTP/1.1 401
WWW-Authenticate: Basic realm="shop"
Content-Type: application/json

{"status":401,"error":"Unauthorized","message":"Authentication is required. Send a valid username and password.","path":"/products"}
```
A wrong password gives the same answer (`curl -u admin:wrong localhost:8080/products`): the API does not say whether the *user* or the *password* was wrong, so nobody can find out which usernames exist. The right password:
```bash
curl -u admin:admin123 localhost:8080/me
curl -s localhost:8080/hello
```
```text
{"username":"admin","authorities":["ROLE_USER"]}
{"message":"Hello, world!"}
```
`curl -u cashier:cashier123 localhost:8080/products` and the same with `admin:admin123` answer `200` with the product list.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| Every request is `401`, even with the right password | The users table is empty (the seeder did not run), or the password was changed after the first start | Delete the folder `shop-data` (a learning database) and start again |
| Log line `Encoded password does not look like BCrypt`, and every login is `401` | The stored password is plain text, not a hash | Store `encoder.encode(password)` (delete `shop-data` to start again) |
| `401` in a test that should be signed in | The test class has no `@WithMockUser` and no `httpBasic(...)` | Add one; for a `@WebMvcTest` also `@Import(SecurityConfig.class)` |
| `403` on every `POST` in a slice test | The slice used Spring's default security, which has CSRF on | `@Import(SecurityConfig.class)` so the slice uses the app's rules |
| `Failed to load ApplicationContext` in a test with `webEnvironment = NONE` | The security filter chain needs a web application | Use the default web environment |
| Browser shows a login pop-up | That is HTTP Basic working: `WWW-Authenticate` asks the browser to prompt | Expected; the `curl -u` form is the same thing |
| The password is visible in the log or in a screenshot | Someone printed the header or the setting | Never log credentials; use `mask(...)` (exercise 5) |
| You are tempted to use `SHA-256` or `MD5` for passwords | They are fast, which is what an attacker wants | BCrypt (or Argon2) from a library |
| `HTTP 401` from `curl` with special characters in the password | The shell changed the characters | Put the credentials in single quotes: `-u 'admin:pa$$word'` |

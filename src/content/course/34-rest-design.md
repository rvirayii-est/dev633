## 1. Learning objectives
After this lesson you can:
- **explain** REST in your own words: things (resources) have addresses (URLs); you act on them with a few verbs (methods); the answer says how it went (status code);
- **design** an API for the shop on paper: which URLs, which method, which status for success, which for each problem;
- **choose** a status code: why "not enough stock" is `409` and not `400`, why creating is `201` and not `200`, why delete is `204`;
- **explain** what *idempotent* means and why `PUT` and `DELETE` have it and `POST` does not;
- **write** a table of the API as data (`ApiDesign`) and a test that makes the code obey it.

## 2. Plain-English explanation
In lesson 33 the server understood any request we hard-coded: `/products`, `/sales`. Each new feature meant new `if` lines and new ideas about what to answer. **Design** means deciding these things *once*, with rules, so that anyone (including you in six months) can guess the next URL.

**REST** (REpresentational State Transfer) is a set of habits for HTTP APIs. It is not a library. The habits:

1. **Everything is a resource**, a *thing* with a name: a product, a sale, a report. The URL names the thing, so the path is a **noun in the plural**: `/products`, `/sales`. *Not* `/getProducts` or `/createSale`.
2. **The method is the verb.** The same URL does different jobs with different methods:
   - `GET /products`: read the list; `GET /products/Rice%2025kg`: read one;
   - `POST /products`: create a new one; `PUT /products/Rice%2025kg`: change one; `DELETE /products/Rice%2025kg`: remove one.
3. **The status code says how it went** (lesson 33). Success has several shapes: `200 OK` (here is your answer), `201 Created` (a new thing exists, and the `Location` header says where), `204 No Content` (done, nothing to say).
4. **Stateless:** every request carries what the server needs. No "remember me from last time".

A thing can contain things: `/products/Rice%2025kg/stock` is the *stock* of one product. `POST` there means "add a delivery". Options such as filters go in the **query**: `/products?status=LOW`. They do not go in the path.

### Idempotent: safe to repeat
A method is **idempotent** if doing it twice leaves the server in the same state as doing it once. This matters on a slow phone connection: if the answer got lost, can the app just send it again?
- `GET`, `PUT`, `DELETE`: yes. Setting the price to 1300 twice is the same as once. Deleting twice leaves it deleted (the second answer is `404`, but the *state* is the same).
- `POST`: **no.** Two `POST /sales` make two sales. (That is why real shops show "are you sure?" before paying.)

### The design of the shop's API
This table is the **contract**. It is also `ApiDesign.ENDPOINTS` in the code, and a test checks the code against it.

| Method | Path | Success | What it does |
|---|---|---|---|
| `GET` | `/products` | `200` | list the products (optional `?status=OK`, `LOW` or `OUT`) |
| `GET` | `/products/{name}` | `200` | one product |
| `POST` | `/products` | `201` | create a product (it starts with 0 in stock) |
| `PUT` | `/products/{name}` | `200` | change a product's price and reorder level |
| `DELETE` | `/products/{name}` | `204` | delete a product that has no history |
| `POST` | `/products/{name}/stock` | `200` | receive a delivery: add units to the shelf |
| `GET` | `/sales` | `200` | list the sales (optional `?payment=CASH`, `GCASH` or `CARD`) |
| `GET` | `/sales/{number}` | `200` | one sale (a receipt) |
| `POST` | `/sales` | `201` | record a sale |
| `GET` | `/reports/stock` | `200` | the stock report |
| `GET` | `/reports/sales` | `200` | the sales report |

`{name}` and `{number}` are *variable parts* of the path. Reports are resources too: a report is a thing you can read, so it is `GET /reports/stock`, not `GET /calculateStockReport`.

What you send (the *request body* of `POST` and `PUT`) and what you get back are **plain data**:

| Request | Fields you send | Answer |
|---|---|---|
| `POST /products` | `name`, `price`, `reorderLevel` | `ProductResponse` |
| `PUT /products/{name}` | `price`, `reorderLevel` | `ProductResponse` |
| `POST /products/{name}/stock` | `quantity` | `ProductResponse` (with the new quantity) |
| `POST /sales` | `product`, `quantity`; optional `customerName`, `customerPhone`, `discount` (`none`, `percent:10`, `fixed:50.00`, `senior`), `payment` (`CASH`, `GCASH`, `CARD`; default cash) | `SaleResponse` |

The answers are small Java **records** called *DTOs* (data transfer objects): `ProductResponse`, `SaleResponse`, `StockReportResponse`, `SalesReportResponse`. Why not send the `Product` class itself? Because the shape of an API is a **promise to every client**. If somebody adds a field to `Product` next month, the API must not change by accident. A DTO copies exactly the fields you decided to promise (lesson 35 shows what goes wrong without one).

### Errors: one shape, and the right number
Every error answer has the same four fields, so a client writes one piece of code to read them all: `status`, `error` (the standard words), `message` (for a person) and `path`. Which exception gives which status is decided in **one place**, `ErrorMapper`:

| Problem | Status | Why |
|---|---|---|
| `UnknownProductException`, `UnknownSaleException` | `404 Not Found` | no such thing |
| `InvalidInputException` (blank name, price 0, quantity 0, bad discount code) | `400 Bad Request` | the caller sent something wrong |
| `InsufficientStockException` | `409 Conflict` | the request is fine, but it clashes with the stock we have *now* |
| `ProductAlreadyExistsException` | `409 Conflict` | the name is taken |
| `ProductInUseException` (delete a product with history) | `409 Conflict` | history must keep pointing at a real product |
| a path that does not exist | `404` | |
| a path that exists with another method | `405 Method Not Allowed` + `Allow` header | |
| anything unexpected (a bug) | `500` with a **generic** message | never show a client our stack trace |

`400` vs `409`: with `400` the caller must *change the request* (nothing would make "quantity 0" valid). With `409` the same request may succeed later (after a delivery arrives).

### How the code is organised
```
Request --> ShopApi (routes) --> ShopService (the rules, lesson 30-31) --> repositories --> database
                |                                                              
                +-- ErrorMapper: exception -> status        ApiDesign: the table as data
```
- `ShopApi.handle(ApiRequest)` returns an `ApiResponse`. It has **no web server inside**: a request is plain Java data (method, path, query, body as a `Map`), so tests call it directly, fast and without a network. A route is a method, a path pattern like `/products/{name}` and a handler.
- The body arrives as a `Map` because a JSON reader does not exist yet. `Body` pulls fields out of it and complains in plain English. Writing `Body` by hand is the chore that lesson 35 removes.
- Two small additions to the shop core, because the API needs them: `ShopService.updateProduct` (price and reorder level) and `ShopService.deleteProduct` (refused with `ProductInUseException` when the stock log or a sale mentions the product), plus `ProductRepository.delete`. They are tested on the in-memory repositories *and* on H2.
- `ShopHttpServer` from lesson 33 is still here, unchanged. Lesson 35 puts `ShopApi` behind a real server.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `theApiHasExactlyTheEndpointsOfTheDesignTable` fails | You added a route in `ShopApi` but not in `ApiDesign` (or the other way round) | Keep the two lists in the same order and the same spelling |
| `Add a sample request for ...` | You added a row to `ApiDesign` and the test does not know a valid example call | Add a `case` to `sampleRequest` in `ApiDesignTest` |
| A path such as `/getProducts` or `/products/create` | A verb in the path | The method is the verb: `POST /products` |
| Using `200` after `POST` that creates | Habit | Answer `201` and set `Location` to the new thing |
| `400` for "not enough stock" | The request itself is valid | `409 Conflict`: the clash is with the current state |
| `404` for a wrong method on a real path | The router only looks at the path | Check all routes of the path first and answer `405` with `Allow` (see `ShopApi.handle`) |
| Details of an exception sent to the client (`NullPointerException at ...`) | Only the message was handled for shop exceptions | Anything not a `ShopException` becomes a generic `500`; log the details on the server |
| Product names with a `/` do not work | `/` splits the path | Not supported on purpose here; real systems use ids (the database id) as the URL |
| Test says `ClassCastException ... ErrorResponse cannot be cast to ProductResponse` | The call failed and returned an error; the test then cast it | Print `response.body()` to see the error message |

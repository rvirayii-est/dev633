## 2. Plain-English explanation
- **Why not `System.out.println`?** `println` goes to the screen for the *user*. A **log** is a record for the *people who look after the program*: what happened, when, how serious. When the shop owner says "yesterday afternoon a sale went missing", a log file is the only witness. `println` cannot be switched off, filtered, timestamped or sent to a file without editing every line.
- **java.util.logging (JUL)** is built into Java, so no library is needed. The four pieces:
  | Piece | Job | In the app |
  |---|---|---|
  | `Logger` | receives messages; one per class, named after it (`Logger.getLogger(Inventory.class.getName())`) | `private static final Logger LOG` in `Inventory`, `Menu`, `DataStore`, `Main` |
  | `Level` | how serious; a logger ignores messages below its level | `Level.INFO` in production, `FINE` when hunting a bug |
  | `Handler` | where the message goes: `ConsoleHandler` (stderr), `FileHandler` | file `shop-data/shop.log` + console for warnings and worse |
  | `Formatter` | how one line looks | our `LineFormatter` |
- **Levels, most to least serious.**
  | Level | Use it when | Example in the shop |
  |---|---|---|
  | `SEVERE` | the program cannot do its job; a person must act | `The shop data cannot be used: products.csv, line 3: ...` |
  | `WARNING` | something unexpected, but the program carried on | a refused sale (`Refused: Unknown product: salt`), an old-format file being upgraded |
  | `INFO` | a normal event worth keeping | a sale, a delivery, `Saved 4 products ...` |
  | `FINE` / `FINER` / `FINEST` | detail for debugging; off by default | `Detail: ...` |
  Production runs at `INFO`. When a bug is hard to see, set the level to `FINE` (one line in `main`) and read the detail; no other code changes.
- **Logging well.**
  - **Log events, not noise.** A line per sale is useful; a line per loop pass is a flood.
  - **Say what, with the values.** `Sale #1: 3 x Rice 25kg for PHP 3,751.50 (Cash)`, not `sale done`.
  - **Log once.** Do not log an exception *and* rethrow it: you get the same problem at every layer. Log it where it is finally handled (`Main` logs the `SEVERE` once).
  - **Never log secrets or private data**: passwords, tokens, full card numbers, customers' phone numbers. A log file is copied, e-mailed and read by many.
  - **Keep the exception.** `LOG.log(Level.SEVERE, "message", exception)` keeps the stack trace; `"..." + e.getMessage()` throws it away.
  - **Don't build expensive text for nothing.** Placeholders (`"Received {0} x {1}"` with an `Object[]`) and a lambda (`LOG.info(() -> "..." + costly())`) only do the work when the level is on. Avoid apostrophes in placeholder messages: `MessageFormat` treats `'` specially.
- **Who decides where logs go?** Not the classes. `Inventory` only says `LOG.info(...)`. `Main` calls `AppLogging.start(...)` once to attach a `FileHandler` (new lines go to the end of the file) and a `ConsoleHandler` for warnings. Loggers form a tree by name: `dev.javabybuilding.inventory.Inventory` is a child of `dev.javabybuilding`, so one handler on the parent catches all of them. At the end `AppLogging.stop(...)` closes the file (and removes the `.lck` lock file Java creates next to it).
- **Quiet and testable.** By default JUL prints every INFO line to the console; that would flood the test report. The module's `pom.xml` points surefire at `src/test/resources/logging.properties` (no handlers), so tests print nothing. Tests that check logging attach a small `ListHandler` to *one* logger and read the records it kept (`LoggingTest`). Remember to detach it afterwards, as `@AfterEach` does.
- **Clean code: five habits.** "Code is read ten times for each time it is written." Refactoring means changing how code is written without changing what it does; **the tests are the proof**.
  1. **Names that say what and why.** `isSeniorOrPwd(customer)` beats `chk(c)`. Names of booleans read as questions; methods start with a verb.
  2. **No magic numbers.** `if (choice == 3)` becomes `case RECORD_SALE`. `0.2` becomes `SENIOR_PWD_DISCOUNT`.
  3. **Small methods, one job, one level of detail.** If you need "and" to describe a method, split it. `Inventory.sell` was checking stock, building a sale, awarding points and recording a movement; now it reads as those steps, and `recordSale` holds the detail.
  4. **Guard clauses instead of pyramids.** Handle the exceptional cases first and `return` (or `throw`); the main path stays at the left margin.
  5. **Comments explain *why*, not what.** If a comment explains what a line does, the name is wrong. Delete dead code (Git remembers it).
  Not a rule: shortest code. The goal is the code the next person understands fastest.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| Nothing appears in the log | The logger's level is higher than the message's, or no handler is attached | Check `LOG.setLevel`/`isLoggable`, and that `AppLogging.start` ran |
| Every message appears twice | The parent's default console handler and yours both print | `logger.setUseParentHandlers(false)` on the logger that has your handler |
| `FINE` messages never show although the logger is at `FINE` | The **handler** has its own level (default `INFO` for a console handler) | `handler.setLevel(Level.FINE)` |
| A test sees logs from another test | Handlers attached to a logger are shared by the whole JVM | Detach in `@AfterEach` (see `ListHandler.stop`) |
| The log configuration "disappears" in a test | A `Logger` nobody holds a reference to can be garbage collected, losing its settings | Keep the logger in a field (`private static final Logger LOG`) |
| `{0}` appears literally in the log | The message has placeholders but no parameters were passed (or you used `info(String)`) | `LOG.log(Level.INFO, "...{0}", value)` |
| Quotes vanish from a message with placeholders | `MessageFormat` uses `'` as an escape | Avoid apostrophes in those messages, or write `''` |
| `shop.log.lck` is left behind / the folder cannot be deleted on Windows | The `FileHandler` was never closed | Call `AppLogging.stop` (in `finally`) |
| The refactor broke a test | You changed behaviour, not only structure | Undo the last small step; refactor in steps of a few lines, running the tests each time |
| The log contains a customer's phone number | Too much was put in the message | Log ids and names the owner needs, never private details |

## 2. Plain-English explanation
Lessons 33-35 built a complete web API from the JDK and Jackson. It works, but look at what **you** had to write: the server, the routing (`if first.equals("products")...`), reading and writing bodies, status codes, JSON setup, headers. None of that is *about the shop*. **Spring Boot** is a framework (a ready-made structure you fill in) that does all of it for you, so you write only the shop's part.

Two words you need:
- **Spring** (the Spring Framework) is a library whose heart is a **container**: a box that creates your objects and hands each one the other objects it needs. Spring MVC, in it, turns web requests into method calls.
- **Spring Boot** is Spring with the boring set-up done for you. It chooses compatible versions, starts a web server inside your program, and configures the libraries it finds. Almost every Java job posting that says "Spring" means this.

### Beans and dependency injection (the container)
A **bean** is an object the container creates and manages. Three ways to get one:
1. Mark a class: `@RestController`, `@Service`, `@Component`, `@Repository`. Spring finds it by *component scanning* (looks through your packages) and creates one.
2. Write a recipe: a method marked `@Bean` inside a `@Configuration` class. Spring calls it once and keeps the result.
3. Auto-configuration (below) creates beans for you.

Look at `ProductController`:
```java
public ProductController(Shop shop) { this.shop = shop; }
```
It *asks* for a `Shop`. Spring looks for a bean of that type (the one `ShopConfig.shop()` made), and passes it in when it creates the controller. This is **dependency injection**: an object receives what it needs from outside, instead of building it. The controller does not know whether the shop keeps data in memory or in a database. In lesson 37 you will swap the shop and not touch the controller. It also makes testing easy: `new ProductController(Inventory.sample())`, no Spring needed (see `ProductControllerTest`). The example `MiniContainer.java` builds a tiny container in 60 lines so you can see there is no magic: it reads the constructor, creates what is needed first, and keeps one object per class.

### The project: what is in the pom
```xml
<dependency>  spring-boot-starter-web  </dependency>
<dependency>  spring-boot-starter-test  <scope>test</scope> </dependency>
<plugin>      spring-boot-maven-plugin  </plugin>
```
- A **starter** is one dependency that stands for a whole set: `spring-boot-starter-web` brings Spring MVC, the Tomcat web server, Jackson and logging. No version number: the root `pom.xml` imports the Spring Boot **BOM** (lesson 35) that fixes all of them to versions that fit (Spring Boot **3.5.16**, which needs Java 17 or later; we use 21).
- `spring-boot-starter-test` is JUnit, AssertJ, Mockito and Spring's test support in one line.
- The Maven plugin adds the command `spring-boot:run` and packages **one runnable jar** with every library inside (`target/shop-api.jar`).
- Real projects usually start at **start.spring.io** (Spring Initializr), a web page where you tick the starters and download a zip. It produces a `pom.xml` like ours. We write ours by hand so you see every line. (Their pom has the Spring Boot *parent*; this course has its own parent, so the lesson pom adds two small settings the Spring parent normally adds: `-parameters` and the `repackage` goal. Comments in the pom say so.)

### The code: only three small things
```java
@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) { SpringApplication.run(ShopApplication.class, args); }
}
```
That is the whole "server". `@SpringBootApplication` means three things: *this class can declare beans*, *scan this package and below for components*, and *auto-configure what the class path suggests*. (So this class must sit in the top package, `dev.javabybuilding`.)

```java
@RestController
public class HelloController {
    @GetMapping("/hello")
    public Greeting hello(@RequestParam(defaultValue = "world") String name) { ... }
}
```
- `@RestController`: the methods answer web requests, and what they return is written as the response body. A `Greeting` record becomes `{"message":"Hello, Ana!"}`.
- `@GetMapping("/hello")`: answers `GET /hello`. (`@PostMapping`, `@PutMapping`, `@DeleteMapping` follow.)
- `@RequestParam`: a value from the query (`/hello?name=Ana`). `@PathVariable`: a variable part of the path (`/products/{name}`).
- Status codes: a normal return is `200`. To answer something else you throw `new ResponseStatusException(HttpStatus.NOT_FOUND, message)`, which `ProductController` does for an unknown product. Lesson 39 gives this a proper home.

Compare with lesson 33: no `HttpServer`, no routing `if`s, no `Http.segments`, no `Content-Type`. And with lesson 35: no `JsonServer`, no `Json.write`. **Three annotations did all of it.**

### Auto-configuration: "I never wrote a web server"
When the app starts, Spring Boot looks at the **class path** (the libraries present) and at your beans, and decides what to set up. Each decision is a rule such as "if `DispatcherServlet` is on the class path *and* the app is a web app, create the web MVC machinery". There are about 150 such rules; most do not match. You can read every decision with the flag `--debug`:
```bash
java -jar lessons/36-spring-boot-hello/solution/target/shop-api.jar --debug
```
It prints a long report; the parts that matter are in section 6. Remember the shape:
- **Positive matches:** `JacksonAutoConfiguration matched: @ConditionalOnClass found required class 'com.fasterxml.jackson.databind.ObjectMapper'`. Jackson is there, so a configured `ObjectMapper` bean exists (the test `ShopApplicationTest` injects it although no class of ours creates it).
- **Negative matches:** `DataSourceAutoConfiguration: Did not match: ... EmbeddedDatabaseType ...`. No JDBC starter is present, so no database is set up. In lesson 38 you add one and this line flips to *matched*.

The rule of thumb: **your own `@Bean` always wins over auto-configuration.** Auto-configuration is a polite default.

### Settings: `application.properties`
`src/main/resources/application.properties` holds settings: `server.port=8080`, `spring.application.name=shop-api`, `server.error.include-message=always`. The same setting can also come from the command line (`--server.port=9090`) or an environment variable (`SERVER_PORT=9090`), and the **most specific wins**: command line, then environment, then the file, then the default. Exercise 4 writes that rule.

### What changed in the app
The console menu, CSV and `ShopHttpServer` code is gone from this module; so are `ShopApi` and `JsonServer`, which Spring now replaces. The shop core (`inventory`), the response and request records (`api`), `ErrorMapper` and `ApiDesign` carry on. New: `ShopApplication`, `ShopConfig` (the `Shop` bean: for now the in-memory sample shop), `HelloController`, and a first `ProductController` with two read-only endpoints.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `Unable to find a @SpringBootConfiguration` | The `@SpringBootApplication` class is missing, or it is in a package that is not above the test | Annotate `ShopApplication` and keep it in the top package |
| `Web server failed to start. Port 8080 was already in use.` | Another program (maybe an older copy of this app, or lesson 33's server) uses 8080 | Stop it, or `--server.port=9090` |
| `No qualifying bean of type 'Shop' available` | No `@Bean` method (or no `@Configuration` class) provides a `Shop` | Put `@Bean` on `ShopConfig.shop()` and `@Configuration` on the class |
| `Name for argument of type [java.lang.String] not specified, and parameter name information not available` | The code was compiled without `-parameters` | The pom sets `maven.compiler.parameters`; run `./mvnw clean ...` so everything is recompiled |
| A controller class exists but `/hello` gives 404 | The class is outside the scanned packages, or lacks `@RestController` | Move it under `dev.javabybuilding`; check the annotation |
| `404` with the text `No static resource ...` | No controller maps that path | Check the spelling of the path and the method (`@GetMapping` answers GET only) |
| `405 Method Not Allowed` from Spring | The path exists but not for that method | Use the right method, or add a mapping |
| `java -jar` says `no main manifest attribute` | The jar was not repackaged (a plain `.jar.original` was run) | Run `package` with the `spring-boot-maven-plugin` as in the pom, then use `target/shop-api.jar` |
| The app starts and exits at once | A `main` that does not call `SpringApplication.run` | Call it, as in `ShopApplication` |
| Changes in `application.properties` have no effect | The file was edited in `target/classes` or the app was not restarted | Edit `src/main/resources`, stop and start again |
| Tests are slow | Every `@SpringBootTest` starts a container | Keep few of them; Spring reuses a started container for tests with the same set-up (lesson 40) |

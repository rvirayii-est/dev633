## 1. Learning objectives
After this lesson you can:
- **draw** the layers of the API and say what each may know: the *controller* knows HTTP, the *service* knows what the app can do, the *repository* knows where the data lives;
- **write** controller methods for `GET`, `POST`, `PUT` and `DELETE`, reading JSON bodies with `@RequestBody` and choosing `200`, `201` or `204`;
- **wire** the shop you built in lessons 29-32 into Spring with a `@Configuration` class, **without rewriting any of it**;
- **run** the full API (products, sales, reports) on a database file, stop it, start it again, and find your data;
- **explain** why the controller catches `ShopException` in every method, and why that repetition is a smell.

## 2. Plain-English explanation
In lesson 36 the only thing behind the endpoints was an in-memory sample. Now the **real shop** goes behind them: the `ShopService`, the three JDBC repositories, the `Database` with its transactions and the `Migrator` of lessons 29-32. The rule for this lesson is simple and is the point of everything before it: **we do not rewrite the shop.** The classes in `dev.javabybuilding.inventory` are untouched. We add a thin web skin around them.

### Three layers
```
HTTP request
   |
   v
Controller   (dev.javabybuilding.api)       knows HTTP: paths, methods, status codes, headers, JSON
   |  calls
   v
Service      (dev.javabybuilding.service)   knows the app's use cases: "create a product", "record a sale"
   |  calls
   v
ShopService + repositories + Database       the rules and the data (lessons 29-32, unchanged)
```
Each layer talks **only to the one below it**. Why bother?
- The **controller** is easy to replace (REST today, a console tomorrow) because it holds no business rules.
- The **service** can be tested with plain JUnit: no server, no JSON (`ProductServiceTest`).
- The **shop core** was already tested in lessons 30-32. We did not touch it, so those tests still stand.
- A rule written in one place is changed in one place.

A good test for where code belongs: does it mention `HttpStatus`, a header or `@RequestBody`? Controller. Does it decide what a sale *means*? Service or core. Does it write SQL? Repository.

### What each layer has in this lesson
| Layer | Classes | Job |
|---|---|---|
| Controller | `ProductController`, `SaleController`, `ReportController` | map URLs to methods, read the body, call the service, choose the status code |
| Service | `ProductService`, `SaleService`, `ReportService` | turn requests into calls on the shop and results into response records |
| Wiring | `ShopConfig` | creates the `Database`, runs the `Migrator`, builds the `ShopService`, seeds the sample |
| DTOs | `ProductResponse`, `CreateSaleRequest` ... | the shapes of the JSON (lesson 34-35, unchanged) |

### Writing controllers
```java
@RestController
@RequestMapping("/products")                 // every method's path starts with /products
public class ProductController {
    private final ProductService products;   // injected: lesson 36
    public ProductController(ProductService products) { this.products = products; }

    @GetMapping                              // GET /products
    public List<ProductResponse> list(@RequestParam(required = false) String status) { ... }

    @GetMapping("/{name}")                   // GET /products/Rice%2025kg
    public ProductResponse one(@PathVariable String name) { ... }

    @PostMapping                             // POST /products   (JSON body)
    public ResponseEntity<ProductResponse> create(@RequestBody CreateProductRequest request) { ... }

    @PutMapping("/{name}")  ...  @DeleteMapping("/{name}") @ResponseStatus(HttpStatus.NO_CONTENT) ...
}
```
- `@RequestBody`: Spring hands the JSON of the request to Jackson and gives you the record, ready.
- A method that just returns an object answers `200`. For anything else use `ResponseEntity` (you pick status, headers and body: `ResponseEntity.created(location).body(...)` is a `201` with a `Location` header) or `@ResponseStatus` (a fixed status, such as `204 No Content` for delete).
- `UriComponentsBuilder.fromPath("/products/{name}").buildAndExpand(name).encode().toUri()` builds the `Location` and URL-encodes the name (`Salt%201kg`). That replaces `ShopApi.encode` of lesson 34.
- Compare with lesson 35's `JsonServer` plus `ShopApi.handle`: the routing table, the `Body`/`Json.convert` step and the status-code plumbing are *gone*. What is left in a controller method is the decision.

### Wiring the old code in: `ShopConfig`
```java
@Bean public Database database(@Value("${shop.database.mode:file}") String mode, ...) { ... Migrator.standard(db).migrate(); }
@Bean public ShopService shopService(Database database, Clock clock) { return new ShopService(...JDBC repositories..., clock, database); }
```
This is `Main.startShop` of lesson 32 written as bean recipes. A parameter of a `@Bean` method is an *ask*: `shopService(Database database, Clock clock)` makes Spring create the database and the clock first. `@Value("${shop.data-dir:shop-data}")` reads a setting from `application.properties` (or the command line) with a default after the colon. Spring closes the `Database` when the app stops, because it has a `close()` method.

Three settings live in `application.properties`: `shop.database.mode` (`file` keeps the data between runs in `shop-data/`; `memory` forgets everything, which the tests use), `shop.data-dir`, and `shop.seed-sample` (an **empty** database is filled once with the four sample products). An `ApplicationRunner` bean does the seeding right after start-up.

### Two honest shortcuts
1. **One request at a time.** `Database` has a single JDBC connection (lesson 29), and Tomcat answers on many threads. So every service method runs inside `synchronized (shop)`: one request talks to the database at a time. It is correct and fine for a small shop. Lesson 38 swaps in a connection pool (HikariCP, which Spring Boot sets up for you): then reading no longer waits, and only the methods that change something keep a lock. The comment `shortcut:` in `ProductService` says so.
2. **Errors are repeated.** Every controller method has
   ```java
   try { ... } catch (ShopException e) { throw Errors.http(e); }
   ```
   `Errors.http` uses `ErrorMapper` (lesson 34) to pick the status and throws a `ResponseStatusException`, which Spring turns into the answer. It works, and you can *see* that it is repetitive. Lesson 39 replaces all of it with one class. Also notice that the error JSON is Spring's own (`timestamp`, `status`, `error`, `message`, `path`), not lesson 34's `ErrorResponse`. Lesson 39 fixes that too.

### The API, as it runs now
Exactly the table of lesson 34 (`ApiDesign`), now served by Spring:

| Method | Path | Success |
|---|---|---|
| `GET` | `/products`, `/products/{name}` | `200` |
| `POST` | `/products` | `201` + `Location` |
| `PUT` | `/products/{name}` | `200` |
| `DELETE` | `/products/{name}` | `204` |
| `POST` | `/products/{name}/stock` | `200` |
| `GET` | `/sales`, `/sales/{number}` | `200` |
| `POST` | `/sales` | `201` + `Location` |
| `GET` | `/reports/stock`, `/reports/sales` | `200` |

One difference you gain for free: a sale number that is not a number (`/sales/abc`) is a `400` made by Spring (the `int number` parameter could not be filled).

One difference you lose, on purpose: **Spring Boot's JSON reader ignores fields it does not know**. Lesson 35's reader refused them. We switch the strictness back on in `application.properties` (`spring.jackson.deserialization.fail-on-unknown-properties=true`), so the typo `reorderLvl` is still a `400`.

### What changed in the app
New: `ShopConfig` (replaces the sample-only version), the `service` package, `SaleController`, `ReportController`, a full `ProductController`, `Errors`. Changed: `application.properties`. Unchanged: all of `inventory`, the DTOs, `ErrorMapper`, `HelloController`. The H2 and `Migrator` of lessons 29-32 run exactly as before.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `Parameter 0 of constructor in ...ProductService required a bean of type 'ShopService' that could not be found` | `shopService` in `ShopConfig` is missing `@Bean`, or returns `null` | Check the recipe; a `@Bean` method must return the object |
| `Database may be already in use` / `Locked by another process` at start | Two copies of the app (or a test) use the same `shop-data` folder | Stop the other one, or use another `--shop.data-dir` |
| `HttpMessageNotReadableException: JSON parse error` (a `400`) | The body is not valid JSON, or has an unknown field, or a value of the wrong kind | Read the message; send `Content-Type: application/json` |
| `415 Unsupported Media Type` | The request has no `Content-Type: application/json` header | Add `-H "Content-Type: application/json"` to `curl` |
| `Required request body is missing` | A POST/PUT without a body | Send the JSON with `-d` |
| `201` but no `Location` | `ResponseEntity.ok(...)` was used, or the header is not set | `ResponseEntity.created(uri).body(...)` |
| `405 Method Not Allowed` | The path exists, but not for that method (for example `DELETE /sales`) | Check the table above |
| Everything works from `curl` but a data file appears in the repo | You started the app from the repo root | `shop-data/` is ignored by Git; start from another folder or pass `--shop.data-dir=...` |
| `@Value` setting is ignored | A typo in the key, or the property is in the wrong file | Keys are case-sensitive; check `application.properties` in `src/main/resources` |
| A test that touches the database leaves state for the next test | The tests share one shop (`ApiIntegrationTest` does it on purpose and runs in a set order) | Prefer a new in-memory shop for each test (`TestShop.sample()`) |
| Requests are slow under load | One connection, one lock | That is the shortcut; lesson 38 uses a pool |

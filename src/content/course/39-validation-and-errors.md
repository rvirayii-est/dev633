## 1. Learning objectives
After this lesson you can:
- **protect** a request with annotations: `@NotBlank`, `@NotNull`, `@Min`, `@DecimalMin`, `@Size`, `@Pattern`, and switch them on with `@Valid`;
- **explain** why a field that must be sent is an `Integer` (can be `null`) and not an `int` (silently becomes `0`);
- **write** a `@RestControllerAdvice` with `@ExceptionHandler` methods, and delete every `try/catch` from the controllers;
- **map** each kind of failure to a status code in one place, and keep the stack trace of a bug in the log, not in the answer;
- **read** an error answer and find the field that is wrong.

## 2. Plain-English explanation
After lesson 38 the API works, but look at how it fails (lesson 37's output):
- a bad request gets Spring's own error JSON, with a `timestamp` that changes every time;
- `POST /products` with no body says `Required request body is missing: public org.springframework.http.ResponseEntity<dev.javabybuilding.api.ProductController.create(...)` — it names **our own Java method**. A client should never see that;
- every controller method repeats the same `try/catch`;
- when three fields are wrong, the client learns about them **one at a time**.

A good API **tells the client everything that is wrong, in one answer, in one shape, without secrets**. Two tools do it.

### Tool 1: Bean Validation (the rules, as annotations)
**Bean Validation** (the standard `jakarta.validation`, implemented by *Hibernate Validator*; you get it with `spring-boot-starter-validation`) lets you write a rule next to the field it protects:
```java
public record CreateProductRequest(
        @NotBlank(message = "is required") @Size(max = 60, message = "must be at most 60 characters") String name,
        @NotNull(message = "is required") @DecimalMin("0.01") @DecimalMax("10000.00") @Digits(integer = 5, fraction = 2) BigDecimal price,
        @NotNull(message = "is required") @PositiveOrZero(message = "must be 0 or more") Integer reorderLevel) {}
```
and switches it on in the controller with one word:
```java
public ResponseEntity<ProductResponse> create(@Valid @RequestBody CreateProductRequest request)
```
Before your method runs, Spring reads the JSON into the record, checks every annotation, and, if any rule is broken, throws `MethodArgumentNotValidException` **with all the broken rules in it**. Your method does not run.

| Annotation | Meaning |
|---|---|
| `@NotNull` | must be sent (not `null`) |
| `@NotBlank` | text with at least one visible character (`null`, `""` and `"   "` fail) |
| `@Size(max = 60)` | length of text (or size of a list) |
| `@Min(1)`, `@Max(100)` | whole numbers |
| `@DecimalMin("0.01")`, `@DecimalMax(...)` | money; `@Digits(integer = 5, fraction = 2)` limits the decimals |
| `@Positive`, `@PositiveOrZero` | shorthand for "more than 0" and "0 or more" |
| `@Pattern(regexp = "...")` | text must match a regular expression |
| `@Valid` | "go inside this object and check its rules too" |

Things beginners trip over:
1. **`Integer`, not `int`.** If a client forgets `reorderLevel`, a field of type `int` quietly becomes `0` and nobody knows. An `Integer` stays `null`, and `@NotNull` can say "is required".
2. **Most rules ignore `null`.** Only `@NotNull`, `@NotBlank` and `@NotEmpty` complain about a missing value. So an *optional* field (`discount`, `payment`) gets `@Pattern` and **no** `@NotNull`: when the client leaves it out, there is nothing to check.
3. **`@Valid` is what switches it on.** Annotations without `@Valid` are just labels. (`MiniValidator.java` shows how little magic there is: something reads the labels and acts.)
4. Parameters can have rules too: `@RequestParam @Pattern(...) String status` and `@PathVariable @Min(1) int number`. Spring 6 checks them for you and throws `HandlerMethodValidationException`.
5. **Validation does not replace the shop's rules.** The shop core still refuses a price of 0 for *every* caller (a script, a test, a second app). Validation at the edge gives the client a *friendlier, complete* answer, and checks the request's **shape**; the rules about stock and prices stay in the domain.

### Tool 2: one place for every failure (`@RestControllerAdvice`)
`ApiExceptionHandler` is a class marked `@RestControllerAdvice`: advice for all controllers. Each method marked `@ExceptionHandler(SomeException.class)` takes care of that exception. When something throws (a controller, the shop, or Spring before the controller was even called), Spring looks for the most specific handler.

| What happened | Exception | Status |
|---|---|---|
| unknown product / sale | `UnknownProductException`, `UnknownSaleException` | `404` |
| the shop refuses the input | `InvalidInputException` | `400` |
| stock too low, name taken, product has history | `InsufficientStockException`, `ProductAlreadyExistsException`, `ProductInUseException` | `409` |
| a database fault (the shop's `DatabaseException`) | `DatabaseException` | `500`, message hidden |
| a rule on the body is broken | `MethodArgumentNotValidException` | `400` + `problems` |
| a rule on a parameter is broken | `HandlerMethodValidationException` | `400` + `problems` |
| broken JSON, unknown field, wrong kind of value, no body | `HttpMessageNotReadableException` | `400` |
| `/sales/abc` | `MethodArgumentTypeMismatchException` | `400` |
| no such path | `NoResourceFoundException` | `404` |
| path exists, method does not | `HttpRequestMethodNotSupportedException` | `405` + `Allow` |
| body is not JSON | `HttpMediaTypeNotSupportedException` | `415` |
| the database refuses a change (duplicate) | `DataIntegrityViolationException` | `409` |
| any other database trouble, any bug | `DataAccessException`, `Exception` | `500`, message hidden |

The shop's exceptions use `ErrorMapper.statusFor` from lesson 34. **That table has not changed since lesson 34**; here it finally has a home in Spring. The only addition is `DatabaseException` to `500`, because a broken database is not the caller's fault.

Every handler builds the same `ErrorResponse`:
```json
{"status":400,"error":"Bad Request","message":"The request has invalid fields.","path":"/products",
 "problems":[{"field":"name","message":"is required"},{"field":"price","message":"must be at least 0.01"}]}
```
`problems` appears only when there are bad fields. There is no `timestamp` on purpose: an answer with a moving part cannot be compared in a test.

### Three rules of good error answers
1. **One shape.** A client writes one piece of code to read any failure.
2. **Tell everything at once, name the field.** The client fixes the whole form in one round trip. The problems are sorted by field name so the answer is always in the same order.
3. **Never leak.** For a bug (`NullPointerException`, a SQL error) the log gets the stack trace, and the client gets `"Something went wrong on the server."` Class names, SQL, file paths and the library versions help an attacker and help nobody else. Look at `unreadableBody`: Jackson's own message would name `dev.javabybuilding.api.CreateProductRequest`; we write our own sentence instead.

### What changed in the app
New: `ApiExceptionHandler`, the rules on `CreateProductRequest`, `UpdateProductRequest`, `ReceiveStockRequest` and `CreateSaleRequest`, `ErrorResponse.problems`, the `spring-boot-starter-validation` dependency. Changed: the controllers (all `try/catch` gone, `@Valid` added, rules on `status`, `payment` and the sale number), the three request numbers are `Integer`, `ErrorMapper` (+`DatabaseException`). Removed: `Errors` and `Checks` (their jobs moved to the advice and to the annotations). **Unchanged: the shop core, the services, the persistence.**

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| A bad body is accepted | `@Valid` is missing on the `@RequestBody` parameter | Add `@Valid` |
| `@NotNull` never fires for a number | The field is `int` (a missing value became `0`) | Use `Integer` |
| An optional field is rejected when left out | You added `@NotNull`, or a rule that rejects `null` | Optional fields get only `@Pattern`/`@Size` (they ignore `null`) |
| `@Pattern` on a number does nothing or fails to start | `@Pattern` is for text | Use `@Min`/`@Max` for numbers |
| `HV000030: No validator could be found for constraint ... validating type ...` | A rule used on a type it does not support (`@Size` on an `int`) | Pick the rule for the type |
| Rules on a path variable or parameter are ignored | Older Spring needs `@Validated` on the class; Spring 6.1+ checks them by itself | Make sure the constraint is on the parameter, and the app uses Spring Boot 3.2+ |
| An exception reaches the client as Spring's own JSON (`timestamp`...) | No `@ExceptionHandler` matches it | Add a handler, or let the `Exception` safety net take it |
| A handler for `Exception` seems to swallow a more specific case | You expected the safety net to run first | Spring picks the **most specific** handler for the exception type; test each status, as `ApiErrorsIntegrationTest` does |
| The answer shows `dev.javabybuilding...` or SQL | A handler returns `e.getMessage()` of a library exception | Write your own sentence; log the exception |
| The errors test fails because the order of `problems` changes | Problems were not sorted | Sort by field and message (`PROBLEM_ORDER`) |
| `MethodArgumentNotValidException` is not caught for a `@RequestParam` | Parameters throw `HandlerMethodValidationException` (a different class) | Handle both, as `ApiExceptionHandler` does |
| A test expects `ResponseStatusException` (lesson 37) | The controller no longer converts anything | Expect the shop's own exception; the advice does the conversion |

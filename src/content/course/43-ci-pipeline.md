## 1. Learning objectives
After this lesson you can:
- **explain** *continuous integration* (CI): a machine that builds and tests every change, so a broken change is found in minutes, not weeks;
- **read** a GitHub Actions workflow: `on`, `jobs`, `steps`, `uses`, `run`, `with`;
- **write** a pipeline for *your own* fork or project that builds and tests on every push and every pull request;
- **speed it up** with a dependency cache and **show its status** with a badge in your README;
- **check** a workflow file with a test, and keep it safe: read-only permissions, actions pinned to a version, no secrets in the file.

## 2. Plain-English explanation
"It works on my computer" is not good enough. Your computer has a Maven cache full of libraries, a JDK you installed once, and files nobody else has. **Continuous integration** is a rule: *every* change is built and tested on a **clean machine** that has only what the repository gives it. If the build is green, the change is safe to merge. If it is red, you find out in minutes, while you still remember what you changed.

**GitHub Actions** is GitHub's free CI (free for public repositories; private ones get a monthly allowance that GitHub may change, so check the current limits). You describe the pipeline in a YAML file in `.github/workflows/`, and GitHub runs it for you.

### The words
| Word | Meaning |
|---|---|
| **workflow** | One YAML file in `.github/workflows/`. A repository can have several |
| **trigger** (`on:`) | What starts it: a push, a pull request, a schedule, a button |
| **job** | A group of steps that run one after another on one fresh machine (`runs-on: ubuntu-latest`) |
| **step** | One thing to do: either `run:` a command, or `uses:` a ready-made *action* |
| **action** | A reusable step written by someone else, such as `actions/checkout` |
| **runner** | The machine GitHub gives you for the job. It is erased afterwards |
| **cache** | Files kept between runs, so you do not download the same libraries again |
| **artifact** | Files a run saves for you to download (for example failed-test reports) |

### This repository's own pipeline, line by line
This is `.github/workflows/ci.yml`, the file that checks the whole course on every push:
```yaml
name: CI
```
The name shown in the *Actions* tab and in the badge.
```yaml
on:
  push:
    branches: [main]
  pull_request:
```
**Triggers.** Run when someone pushes to `main`, and on every pull request (to any branch). Pull requests are where CI earns its keep: it tells the reviewer "this change builds" before anybody reads the code.
```yaml
permissions:
  contents: read
```
The workflow may only **read** the repository. A build has no reason to write to it, and if a workflow is ever abused, read-only limits the damage.
```yaml
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```
If you push twice in a row to the same branch, the first run is cancelled. Nobody waits for a commit that is already out of date. `${{ ... }}` is how a workflow reads a value (here the branch name).
```yaml
jobs:
  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 30
```
One job, called `verify`, on a fresh Ubuntu machine. If it runs longer than 30 minutes it is stopped: a stuck build must not use up your allowance.
```yaml
    steps:
      - uses: actions/checkout@v4
```
Step 1: copy the repository onto the machine. Without it the machine is empty. `@v4` pins the version of the action, so the action cannot change under you.
```yaml
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "21"
          cache: maven
```
Step 2: install Java 21 (the Temurin build of OpenJDK). `cache: maven` saves the folder `~/.m2` at the end of a green run, under a key made from the hash of every `pom.xml`, and restores it at the start of the next run. Same poms, same key, no downloads. Change a dependency and the key changes, so the cache is rebuilt. (Exercise 5 builds such a key.) `"21"` is in quotes so YAML reads it as text, not as a number: `"21.0"` and `21` can differ.
```yaml
      - name: Every lesson README has its front matter and its eight sections
        run: java scripts/LessonTool.java check
      - name: lessons/index.json is up to date
        run: java scripts/LessonTool.java index --check
```
Two cheap checks first, in seconds: *fail fast*, so a typo in a README does not wait behind a five-minute build. (Both commands are one small Java file of this repository, `scripts/LessonTool.java`; see `CONTRIBUTING.md`.)
```yaml
      - name: Reference solutions build and tests pass
        run: ./mvnw -B verify
      - name: Starters and exercises compile (their tests are expected to fail)
        run: ./mvnw -B -Pstudent test-compile
      - name: Every lesson example runs
        run: bash scripts/run-examples.sh
```
The three promises of the course. `./mvnw` is the Maven wrapper (nothing to install); `-B` is *batch mode*: no colours or progress bars, which would turn a log into noise. Starters and exercises are only *compiled* because their tests fail on purpose until a student finishes them.
```yaml
      - name: Keep the test reports when something failed
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: surefire-reports
          path: "**/target/surefire-reports"
          retention-days: 7
```
`if: failure()` makes this step run **only when an earlier step failed**. It saves the test reports as a download, because the runner is erased and the reports would be lost. Steps stop at the first failure unless they say otherwise, which is why this one needs the `if`.

### Your own pipeline
`solution/ci/student-ci.yml` is the same idea reduced to what a single project needs: checkout, Java 21 with the Maven cache, `./mvnw -B verify`, reports on failure. Copy it to `.github/workflows/ci.yml` in your fork or project, commit, push, and open the *Actions* tab.

### A status badge
A *badge* is a small picture, made by GitHub, that says "passing" or "failing". Put this line at the top of your README (replace `OWNER` and `REPO`):
```markdown
[![CI](https://github.com/OWNER/REPO/actions/workflows/ci.yml/badge.svg)](https://github.com/OWNER/REPO/actions/workflows/ci.yml)
```
Employers who open your repository see at once that the project builds. Exercise 1 writes this line in Java.

### Safe habits
- **Pin actions** to a version (`@v4`) or, to be strict, to a full commit id. `@main` runs whatever the author pushes tomorrow.
- **Least permission** (`permissions: contents: read`). Add more only for a job that needs it.
- **No secrets in the file.** A password or token in YAML is public for ever once pushed. If a job needs one (to publish somewhere), keep it in the repository's *Settings, Secrets* and read it as `${{ secrets.NAME }}`. Our pipelines need none.
- **Pull requests from forks** do not get your secrets, on purpose.
- **A green pipeline is not proof of quality.** It proves the tests you wrote pass. Weak tests give a green tick that means little.

## 4. Step-by-step: build a pipeline for your project
1. Read `solution/ci/student-ci.yml` from the top, with the explanation above next to it.
2. In `starter`, open `ci/student-ci.yml`. It builds, but is missing six things (TODO 1 to 6). Run `../../../mvnw test -Dtest=CiWorkflowTest` and fix one failure at a time: each message names the missing property.
3. **YAML is picky about spaces.** Use 2 spaces per level, never tabs. A list item starts with `- `. If a test says the YAML is invalid, look at the indentation first.
4. Make your own repository (or your fork of this course): copy the finished file to `.github/workflows/ci.yml` and push. Open *Actions* and watch the run. The first run is slow (no cache); push a small change and compare the time of the second.
5. Add the badge to your README (exercise 1 has the exact line).
6. Break it on purpose: change one assertion in a test, push to a branch, open a pull request, and watch the red cross appear. Read the log. Download the test reports from the *Artifacts* section. Fix it, push, and watch it turn green.
7. In your repository's *Settings, Branches*, you can require the check before merging ("branch protection"). That turns CI from advice into a rule.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| The workflow never runs | The file is not in `.github/workflows/` (or is not `.yml`/`.yaml`), or the branch is not in `on.push.branches` | Check the path and the branch name |
| "Invalid workflow file" in the Actions tab | A YAML mistake, usually indentation | Run `CiWorkflowTest` locally, or paste into a YAML checker; use spaces, never tabs |
| `./mvnw: Permission denied` | The wrapper lost its executable bit when it was committed from Windows | `git update-index --chmod=+x mvnw`, commit, push. Or run `bash mvnw -B verify` in the workflow |
| `mvnw: line 1: $'\r': command not found` | Windows line endings in a shell script | Add a `.gitattributes` line `mvnw text eol=lf` and commit the file again |
| Passes on your PC, fails in CI | Your PC has something the repository does not (a file you did not commit, a different Java, a path that only exists on Windows, a test that depends on time or order) | Read the log from the first red line; reproduce with a fresh clone in an empty folder |
| Always slow | No `cache: maven`, or the key changes every run | Check the "Post Set up JDK" step in the log: "Cache saved" then "Cache restored" |
| `java-version: 21` behaves oddly or `"21.0"` becomes `21` | YAML turns an unquoted `21.0` into the number 21 | Quote versions: `"21"` |
| The `on:` section is ignored by your own YAML tool | In YAML 1.1 the bare word `on` is the boolean *true* | GitHub understands it; if your parser does not, look under the key `true` (the test does) |
| A secret shows up in a log | A `run:` printed it | Secrets are masked as `***` by GitHub, but never `echo` them; never put them in the file |
| `Resource not accessible by integration` | `permissions: contents: read` is too little for what the step does | Grant the one permission that step needs, in that job only |
| A job runs for hours | A test waits for input or a port | `timeout-minutes`; then find the hanging test |

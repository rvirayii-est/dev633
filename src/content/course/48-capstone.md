### What M7 is not (be honest about it in your demo)
- **HTTP Basic**, not tokens: the password travels with every request, so it needs HTTPS in front (lesson 41).
- **H2**, a file database: fine to learn and for a demo; a real shop needs PostgreSQL or similar, with backups (lesson 46).
- **One copy of the app.** The locks in the services (`synchronized`) protect one process. Several copies need the database to do the locking.
- **No password change**, no user management, no pagination, no front end, no audit trail of who did what.
- The Docker files were tested as text; building the image needs Docker, which the author's machine did not have (lesson 45).
Knowing the limits of your work is a sign of seniority, not of weakness.

### The worked example: add `GET /reports/low-stock` through every layer
Lesson 40 ended with this checkpoint: "add a new endpoint, `GET /reports/low-stock`, with a test first. Which layers do you touch?" Here is the answer, in the order a careful developer works:
1. **Spec** (one sentence): "The admin can list the products whose status is OUT or LOW, OUT first, each group in name order. A cashier may not."
2. **Service test first** (`LowStockReportTest`, plain JUnit, no Spring): sample shop gives `[Sugar 1kg (OUT), Cooking Oil 1L (LOW)]`; a delivery removes a product; a sale can add one; nothing to report is an empty list, not an error. Red.
3. **Service** (`ReportService.lowStock()`): filter, sort. Green.
4. **Web slice test** (`ReportAndHelloWebTest`, a fake service): the URL, the status and the JSON shape. Then the **controller** method.
5. **Design table** (`ApiDesign.ENDPOINTS`): one more row. Forget it and `ApiDesignMappingTest` fails (lesson 40).
6. **Documentation**: `@Operation(summary = ...)`. Forget it and `OpenApiTest` fails (lesson 44).
7. **Security**: the rule `/reports/**` for admins already covers it; the matrix test `RolesTest` got one more row to prove it (lesson 42). If you had forgotten, the catch-all `hasRole("ADMIN")` would still have kept it closed to cashiers.
8. **The story** (`EndToEndScenarioTest`, real HTTP, security on): the admin reads the low-stock report after a real sale.
Eight small steps, each with a failing test or a failing build that tells you what you forgot. That is what the course has been training: **the tests tell you when you are done.**

### Your capstone
Choose **one feature** that makes the system more useful to a shop, small enough to finish in the week and big enough to touch several layers. Ideas, from easier to harder:

| Idea | Touches |
|---|---|
| `GET /products?name=sa`: search by part of the name | repository query, service, controller, tests |
| `GET /reports/sales?from=2026-03-01&to=2026-03-31`: sales in a date range | validation of dates, repository query, tests |

| Pagination for `/products` and `/sales` | query parameters, `Pageable`, response shape |
| Daily sales summary exported as CSV | streams, `produces = text/csv`, tests of the format |

**Rules.**
1. **Spec first.** One page in your repository: the problem, who uses it, the endpoints (method, path, who may call, success and error statuses), the data (a migration if there is a new table). Your instructor approves it before you code.
2. **Tests first**, at the smallest size that can show each bug (lesson 40's pyramid). At least: unit tests of the rule, a slice test of the endpoint, one end-to-end step.
3. **Through every layer**, as in the worked example: security rule, design table, OpenAPI summary, migration if the schema changes.
4. **Small commits and a pull request** (lesson 23); CI must be green before you merge (lesson 43).
5. **No secrets** in the repository, ever (lesson 46).
6. **Honest README** from the template, and a **5-minute demo**.

### For instructors: the assessment
Competency-based assessment asks "can they do it, and is there observable evidence?", not "how many marks?". Each criterion below is scored **0 no evidence, 1 partly, 2 meets, 3 exceeds**; the student is **Competent** only when **every** criterion is at least 2 (one weak criterion cannot be hidden by strong ones: exercise 4), and the percentage is available as a grade if your institution needs one. Combine the evidence types an assessor normally uses: demonstration, oral questioning, review of the portfolio and the repository.

> This is an *indicative* rubric. Align it with the current TESDA Training Regulations and your assessment centre's tools before using it for certification (see `docs/TESDA-MAPPING.md`).

| # | Criterion | Observable evidence (how to check) | Evidence type |
|---|---|---|---|
| 1 | The software runs from the README | A fresh clone builds with `./mvnw -B verify` and starts; the commands in the README work as written | Demonstration |
| 2 | The feature meets its spec | Each endpoint in the spec answers with the promised status and JSON, for good and for bad input (`400`, `404`, `409` named) | Demonstration |
| 3 | Tests | New tests at more than one size (unit, slice, scenario); the whole build is green; a deliberately broken rule makes a test fail | Repository + demonstration |
| 4 | Security | The new endpoint has a deliberate rule (checked with an admin, a cashier and a stranger); no password or token in the repository (`git grep`) | Demonstration + review |
| 5 | Documentation | The endpoint appears in `/v3/api-docs` with a summary; the README has all ten sections (the checker of exercise 1) | Review |
| 6 | Version control | At least 10 meaningful commits, imperative messages, a pull request with a green check | Repository review |
| 7 | CI | The workflow file exists, the badge in the README is green, the student can show a red run they fixed | Repository + oral questioning |
| 8 | Packaging and configuration | `Dockerfile`/compose present and passing `DockerFilesTest`-style checks; settings from the environment; *if Docker is available*, the image builds and answers. If not, the student explains each line of the Dockerfile | Review + oral questioning |
| 9 | Demo | 5 minutes (+- 20 s), following the script: secured, roles, own feature, documentation, health, proof; handles a failure calmly | Demonstration |
| 10 | Explanation | Asked three questions about the student's own code ("why is this rule first?", "what does this migration do to existing rows?", "what happens if two cashiers sell the last item?"), answers in plain words | Oral questioning |

A one-page record per student (name, date, ten scores, the evidence seen, assessor's signature) is the "observable evidence" the TESDA mapping asks for. Exercise 4 turns the ten scores into the decision.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| The capstone is too big and nothing works by Friday | The spec tried to do three features | Cut to one endpoint that works end to end; list the rest under "What I would do next" |
| A new endpoint answers `403` for the admin | A rule above `/reports/**`-style rules matches first, or the path is not in the rules table | Rules are read top to bottom; check `SecurityConfig` and the matrix test |
| A new endpoint is open to cashiers by accident | A broad `permitAll()` or `authenticated()` rule above it | Specific rules first; the last rule must be the strict catch-all |
| `ApiDesignMappingTest` fails | The controller has a mapping the design table lacks (or the reverse) | Add the row to `ApiDesign.ENDPOINTS` |
| `OpenApiTest ... has no summary` | A new operation has no `@Operation(summary = ...)` | Add it |
| `FlywayException: Detected failed migration` or checksum mismatch | A migration file was edited after it ran | Never edit a released migration; add a new version (V6) |
| Tests pass alone and fail together | Shared in-memory database name between test classes | A different `jdbc:h2:mem:name` per application configuration |
| The README checker says a section is missing, but you wrote it | The heading is `### x` or has a different spelling | Exactly `## ` plus the heading text; capitals do not matter |
| The demo runs over time | Too much explaining | Cut a section; rehearse with a timer; the script shows where |
| A password appears in `git log` | It was committed once | Change it now; history cleanup is a second step (lesson 46) |
| CI is red on GitHub but green locally | Something only your PC has | Fresh clone in an empty folder; read the log from the first red line (lesson 43) |
| An interviewer asks about Docker and you never ran it | The bullet claims more than you did | Say exactly what you did ("wrote and tested the Dockerfile as text; did not build the image") |

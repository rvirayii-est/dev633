## 2. Plain-English explanation
In lesson 29 you wrote SQL strings, `PreparedStatement`s and loops over `ResultSet`s to copy a row into a `Product`. Lesson 30 hid that behind the repository interface. That was good, but look at `JdbcSaleRepository`: 135 lines, nearly all of them copying between rows and objects. It is the same chore for every table. An **ORM** (object-relational mapper) does the copying for you.

- **JPA** (Jakarta Persistence API) is the *standard*: the annotations and rules. It is only an interface, like JDBC.
- **Hibernate** is the library that *implements* JPA: it writes the SQL, runs it and builds the objects.
- **Spring Data JPA** sits on top and writes the *repository classes* for you.
- **Flyway** (lesson 32's Migrator, professional edition) creates and upgrades the tables.
- **HikariCP** is a **connection pool**: a few ready-made database connections that requests borrow and give back. (Lesson 29's single `Connection` made us lock every request; a pool removes that for reading.)

`MiniOrm.java` (examples) shows the idea in 50 lines: read the class (fields become columns, the class name becomes the table), build the SQL, copy values. Hibernate is that, grown up.

### The pieces in the project
```
ShopService  (unchanged since lesson 30)
   |  uses the interfaces ProductRepository, SaleRepository, StockMovementRepository, Transactor
   v
JpaProductRepository, JpaSaleRepository, JpaStockMovementRepository, SpringTransactor    <- "adapters" (new)
   |  call
   v
ProductJpaRepository, SaleJpaRepository ...       <- Spring Data interfaces (you only declare them)
   |  store
   v
ProductEntity, SaleEntity, SaleLineEntity ...      <- entities: Java classes mapped to tables (new)
   |  Hibernate writes the SQL
   v
HikariCP pool  -->  H2 file database, tables made by Flyway from db/migration/V1..V3
```
**Why two kinds of class, `Product` and `ProductEntity`?** `Product` is the domain class: it has *rules* (a price must be 0.01 to 10,000, a quantity cannot go below 0), no id, no setters for the name. A JPA entity must have an empty constructor, an id, and be changeable by the framework. If we made `Product` an entity we would have to weaken its rules. So the entity is the *table row*, the domain class is the *shop's idea of a product*, and the **adapter** (`JpaProductRepository`) converts between them. Cost: a little mapping code. Gain: the domain and `ShopService` do not know JPA exists, so lessons 10-31 stay valid, and so do their tests.

### An entity
```java
@Entity                                  // this class is a table row
@Table(name = "product")                 // the table's name
public class ProductEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   // the primary key; the database makes the number
    private Integer id;
    @Column(nullable = false, length = 60) private String name;
    @Column(nullable = false, precision = 10, scale = 2) private BigDecimal price;
    @Column(nullable = false) private int reorderLevel;       // the column is reorder_level (camelCase -> snake_case)
    @Column(nullable = false) private int quantity;
    protected ProductEntity() {}                               // JPA needs an empty constructor
    ...
}
```
- **Names:** Spring Boot maps the field `reorderLevel` to the column `reorder_level` by itself (camelCase to snake_case); `@Table(name = "product")` says which table. Exercise 1 writes that rule.
- **Relations:** the foreign keys of lesson 28 become object links. `SaleLineEntity` has `@ManyToOne SaleEntity sale` and `@ManyToOne ProductEntity product`: the columns `sale_id` and `product_id` are filled in for you. `SaleEntity` has `@OneToMany(mappedBy = "sale", cascade = ALL) List<SaleLineEntity> lines`: save the sale and its lines are saved too.
- **Enums:** `@Enumerated(EnumType.STRING)` stores `GCASH`, not the number 1. (We add `@JdbcTypeCode(SqlTypes.VARCHAR)`: with H2, Hibernate would otherwise send the enum as H2's own ENUM type, but our column, made in lesson 28, is plain `VARCHAR` with a `CHECK`.)
- **The `active` column** (migration V3) is not mapped: the entity does not know it exists, the database fills its default. Mapping is a choice per column.

### A Spring Data repository
```java
public interface ProductJpaRepository extends JpaRepository<ProductEntity, Integer> {
    Optional<ProductEntity> findByNameIgnoreCase(String name);   // where upper(name) = upper(?)
    List<ProductEntity> findAllByOrderByIdAsc();
}
```
There is **no class**. Spring creates one at start-up. `JpaRepository` already gives `save`, `findById`, `findAll`, `delete`, `count`. A method whose **name** follows the pattern becomes a query: `findBy` + field + `And` + field + `IgnoreCase`... Exercise 4 writes a tiny version of that translator. For anything the name cannot say you write the query yourself with `@Query` in JPQL (SQL on classes and fields), as `SaleJpaRepository.findAllWithDetails` does.

### The adapter: where the two worlds meet
```java
@Repository
public class JpaProductRepository implements ProductRepository {   // the interface of lesson 30
    public void update(Product product) {
        ProductEntity entity = jpa.findByNameIgnoreCase(product.getName()).orElseThrow(...);
        entity.changeTo(product.getPrice(), product.getReorderLevel(), product.getQuantity());
        jpa.save(entity);
    }
    ...
}
```
Compare with `JdbcProductRepository.update` from lesson 29: no SQL, no `PreparedStatement`, no `SQLException`. And `findByName` is one line instead of fifteen.

### Transactions and Flyway, the Spring way
- `SpringTransactor` implements lesson 31's `Transactor` with Spring's `TransactionTemplate`: commit when the work returns, roll back when it throws, join a running transaction. **`ShopService` did not change** (that was the point of the `Transactor` interface). `JpaTransactionTest` breaks a sale half way and checks that the shelf and the receipt were rolled back.
- Delete `Database`, `Migrator`, `Migration`, `Migrations`, `MigrationException` and `index.txt`: **Flyway** does their job, with the **same files** (`V1__create_shop_tables.sql` ...), because lesson 32 chose Flyway's naming. At start-up the log says: `Migrating schema "PUBLIC" to version "1 - create shop tables"` ... `Successfully applied 3 migrations`. Flyway keeps its own history table, `flyway_schema_history`.
- `spring.jpa.hibernate.ddl-auto=validate` makes Hibernate **check** that every entity matches the tables, and refuse to start if not. (Other values let Hibernate *change* your tables. Never use them: migrations own the design, lesson 32.) A wrong column name fails at start-up with `Schema-validation: missing column [reorder_lvl] in table [product]`, not at the first sale.

### JDBC or JPA? An honest comparison
| | JDBC (lessons 29-30) | JPA / Spring Data (this lesson) |
|---|---|---|
| Code you write | a lot: SQL, statements, loops over rows | much less: entities, interfaces |
| You see the SQL | yes, every character | no (turn on `spring.jpa.show-sql=true` to look) |
| Mapping rows to objects | by hand, column by column | by annotations |
| Relations (`sale` has `lines`) | joins and loops by hand | `@OneToMany`, loaded for you |
| Speed problems | you cause them knowingly | easy to cause by accident (N+1, loading too much) |
| Learning curve | small | steep: lazy loading, sessions, cascade, flush |
| Complicated reports | plain SQL, great | possible with `@Query`, sometimes awkward |
| Change the database later | rewrite dialect-specific SQL | the ORM adapts to the dialect |
| Best for | reports, bulk updates, full control | many small reads and writes of whole objects (CRUD) |
Real projects often use **both**: JPA for the everyday create/read/update, plain SQL (or `JdbcTemplate`) for the heavy reports.

### The N+1 problem
Load 5 sales, then ask each for its lines, then each line for its product: the database is asked **1 + 5 + 5 = 11** times, although one query could answer. JPA loads relations *lazily* (only when touched), so this happens quietly. `SaleJpaRepository.findAllWithDetails` uses `join fetch` to read everything in **one** query, and the test `readingAllSalesIsOneQueryNotOnePerSale` counts the statements with Hibernate's statistics. When an API gets slow, look at the SQL first.

### What the services lost: the locks for reading
Reading no longer waits: each request borrows its own connection from the pool. Methods that *change* things keep their `synchronized`, so two sales in this program cannot both take the last bag of rice. (Several copies of the app would need the database itself to lock the row. That is beyond this course.)

### Two quirks of the tools (so they do not surprise you)
- **Flyway prints** `Flyway upgrade recommended: H2 2.4.240 is newer than this version of Flyway` — a harmless warning: the H2 version is newer than the one this Flyway was tested with.
- In database **slice tests** (`@DataJpaTest`) Spring normally swaps your DataSource for its own embedded one. With H2 2.4 that made the `CHECK ... IN (...)` rules fail with `Check constraint invalid ... The database has been closed`. The tests therefore keep the app's pooled DataSource and point it at a memory database, through one composed annotation, `@ShopDataJpaTest`.

### What changed in the app
New: the `persistence` package (5 entities, 4 Spring Data interfaces, 3 adapters, `SpringTransactor`), `SampleDataSeeder`, Flyway and Spring Data JPA dependencies. Changed: `ShopConfig` (Spring provides the database), the services (no locks for reading), `application.properties`, `DatabaseException` (a second constructor). Removed: `Database`, `Migrator`, `Migration`, `Migrations`, `MigrationException`, the three `Jdbc*Repository` classes, `SqlRunner`. **Unchanged: `ShopService`, the domain, the controllers, the DTOs, `ErrorMapper`.** The API behaves exactly as in lesson 37.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `Schema-validation: missing column [reorder_lvl] in table [product]` | The entity field name (or `@Column`) does not match the table | Fix the name; `ddl-auto=validate` did its job |
| `Schema-validation: missing table [xyz]` | The entity has no table: you forgot a migration | Add a `V<next>__...sql` file; never `ddl-auto=update` |
| `No identifier specified for entity` / `Not a managed type` | The class lacks `@Entity` or `@Id`, or is outside the scanned packages | Annotate it; keep entities under `dev.javabybuilding` |
| `Found non-empty schema(s) "PUBLIC" but no schema history table` | The database was made by lesson 32's Migrator | Delete `shop-data`, or `--spring.flyway.baseline-on-migrate=true --spring.flyway.baseline-version=3` |
| `Could not determine recommended JdbcType for Java type ...` | An unusual Java type, or an annotation missing on an enum | `@Enumerated(EnumType.STRING)`; for a custom type use a converter |
| `Check constraint invalid ... The database has been closed` in a test | A `@DataJpaTest` that swapped the DataSource (H2 2.4 quirk, section 2) | Use `@ShopDataJpaTest` |
| `LazyInitializationException: could not initialize proxy - no Session` | You touched a lazy relation after the transaction ended | Load what you need inside the query (`join fetch`), as `findAllWithDetails` does; do not turn laziness off everywhere |
| The app is slow and the log shows hundreds of `select` lines | The N+1 problem | `join fetch` or `@EntityGraph`; look at `show-sql` |
| `DataIntegrityViolationException` on delete | A foreign key still points at the row | `ShopService.deleteProduct` checks the history first; for other tables use the same idea |
| A change to an object is not saved | You changed a domain `Product`, not the entity, and did not call `update` | Repositories only save what you hand back to them (lesson 30) |
| Sale numbers do not start at 1 in a test | The database keeps counting after a rollback | Never assume the first id; compare with the number you were given |
| `Database may be already in use` | Two copies of the app on one `shop-data` | Stop the other, or use `--shop.data-dir=...` |

## 2. Plain-English explanation
*Deploying* means putting the app somewhere other people can reach it and keeping it running. The code is the same as on your PC. What changes is the **place**, and the place changes the **settings**: the port, the folder of the data, the passwords, whether sample products exist. If those settings are written in the code, you rebuild for every place, and sooner or later a real password lands on GitHub. The rule of this lesson (it is the third of the famous "12-factor app" rules: *config in the environment*):

> **Build one artifact. Give it its settings from outside.**

### Three layers of settings
Spring Boot reads settings from several places and the **stronger one wins**:
```text
weakest   application.properties            inside the jar: good defaults for YOUR PC
          application-prod.properties       inside the jar, read only when the profile "prod" is on
          environment variables             set by the server, Docker or the .env file
strongest command-line arguments            java -jar shop-api.jar --server.port=9090
```
- A **profile** is a name for a set of settings. `SPRING_PROFILES_ACTIVE=prod` (or `--spring.profiles.active=prod`) loads `application-prod.properties` on top.
- In a properties file, `${NAME}` means "the value of the variable NAME", and `${NAME:default}` "...or this default if it is missing".
- Spring Boot maps variable names to property names: `SHOP_DATA_DIR` fills `shop.data-dir` (upper case, dots and hyphens become underscores). `ConfigPrecedence.java` replays the layers.

### What the `prod` profile changes (`application-prod.properties`)
| Setting | On your PC | In `prod` |
|---|---|---|
| passwords | `admin123` / `cashier123` (defaults, for learning) | `${SHOP_ADMIN_PASSWORD}` and `${SHOP_CASHIER_PASSWORD}`: **no default**; minimum 12 characters |
| sample products | yes (`shop.seed-sample=true`) | no (`${SHOP_SEED_SAMPLE:false}`) |
| database folder | `./shop-data` | `${SHOP_DATA_DIR:/data}` |
| port | `${PORT:8080}` | `${PORT:8080}` (many hosts set `PORT`) |
| Swagger page | on | off unless `SHOP_SWAGGER_ENABLED=true` (the API description stays) |
| error messages in Spring's own error page | shown | `never` |

### Fail fast, not open
A missing password must stop the application, not start it with a guess. Two things make that true, and the second one is a trap worth knowing:
1. `${SHOP_ADMIN_PASSWORD}` with no default is *meant* to fail when the variable is missing. **But** when Spring binds a `@ConfigurationProperties` object, an unresolved `${...}` is **left as plain text**: the password would become the 22 characters `${SHOP_ADMIN_PASSWORD}` and the app would start happily. The test caught this while the lesson was being written.
2. So the settings are a typed, validated object, `SecuritySettings`: both passwords must be non-blank, at least `minPasswordLength` long (8 on your PC, 12 in `prod`), must not start with `change-me` (the example text) and must not contain `${` (an unfilled placeholder). If any rule fails, the application prints the reason and exits. This is what you see when the variables are missing:
```text
APPLICATION FAILED TO START

Binding to target dev.javabybuilding.security.SecuritySettings failed:

    Property: shop.security.acceptable
    Value: "false"
    Reason: the passwords must be at least minPasswordLength characters long, must not start with 'change-me' and must not be an unresolved placeholder (in the prod profile set the variables SHOP_ADMIN_PASSWORD and SHOP_CASHIER_PASSWORD)
```
A start-up failure with a clear reason is a good outcome: the alternative is a server in the open with a password nobody chose.

### Secrets: where they may and may not live
| Place | OK for a secret? |
|---|---|
| Java source, `application.properties`, `Dockerfile`, `compose.yaml`, any committed file | **No.** Public for ever once pushed (Git remembers deleted files) |
| `.env` next to the compose file, listed in `.gitignore` and `.dockerignore` | Yes, on your own machine. Never commit it (`EnvExampleTest` checks both ignore files) |
| `.env.example` | Only placeholders (`change-me-...`). It documents the names |
| The hosting service's "environment variables" / "secrets" page | Yes: that is what it is for |
| A chat, a screenshot, an issue | **No.** If a secret leaks, change it at once; deleting the message is not enough |
Note also: the seeded passwords are used **only the first time**, when the user table is empty. Changing `SHOP_ADMIN_PASSWORD` later does not change the stored hash. A real system has a "change my password" feature (an exercise for the capstone).

### Where can it live? Honest options
These are *kinds* of places, not recommendations. **Free tiers, limits and prices change often, and some need a payment card even when free. Check the provider's current page before you rely on anything below; none of this is guaranteed.**

| Kind of place | What you do | Typical catch |
|---|---|---|
| **A machine you control** (your PC, a classroom PC, a Raspberry Pi, an old laptop) | Install Docker, run `docker compose up -d` | You are the operator: power, updates, backups. Reachable from the internet only with extra work (a tunnel service or port forwarding) |
| **A platform that builds your Dockerfile from GitHub** (several exist, with and without a free plan) | Connect the repository, point at the Dockerfile, set the environment variables, choose the health-check path | Free plans commonly **put the app to sleep** when idle (first request takes many seconds), have small memory (a JVM needs roughly 300-500 MB to be comfortable) and often an **ephemeral disk**: the H2 file is lost on redeploy |
| **A small virtual machine** (some cloud providers have an always-free or trial tier) | Install Docker on it, copy the compose file, run it | Usually needs a card for sign-up, trial credit ends, you must secure the server yourself (firewall, updates, HTTPS) |
| **A container service of a big cloud provider** | Push the image to a registry, create a service | Free allowance exists, but billing accounts are required and mistakes can cost money |

Things every option shares, and what you must therefore decide:
- **HTTPS.** HTTP Basic sends the password with every request (lesson 41). Over plain HTTP that is readable by anyone on the path. Platforms usually provide HTTPS for you; on your own machine put a reverse proxy (Caddy, nginx) in front or use a tunnel that provides it. **Never expose Basic over plain HTTP to the internet.**
- **Data.** A file database inside a container survives only if the disk does. For anything that matters you want a managed database (PostgreSQL) with backups. Moving there means: the PostgreSQL driver, a connection URL and credentials from the environment, and checking that the Flyway migrations (V1-V5 were written and tested for H2) run on it. That is worth a lesson of its own and is on the roadmap.
- **Health check.** A platform restarts an app that does not answer. Lesson 47 adds `/actuator/health` for that.
- **Logs.** There is no terminal on a platform; the log output is all you get. Lesson 47 makes it structured.

### One concrete path: run the container from a `.env` file
This is the path the lesson tests as far as it can without Docker. It costs nothing and needs no account.
1. `cp lessons/46-deploy/solution/.env.example lessons/46-deploy/solution/.env`
2. Edit `.env`: choose two passwords of **12 or more characters**. Do not keep `change-me`.
3. `docker compose -f lessons/46-deploy/solution/compose.yaml up --build -d`
4. `curl -u admin:<your admin password> localhost:8080/products` answers `200` and `[]` (a real shop starts empty).
5. `docker compose -f lessons/46-deploy/solution/compose.yaml logs -f` shows the log; `down` stops it; `down -v` also deletes the data.
For the internet, the same image can be given to any of the places above. The settings they ask for are the ones in `.env.example`; the *health-check path* to give them is `/actuator/health` (lesson 47).

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `APPLICATION FAILED TO START ... shop.security.acceptable` | A password is missing, shorter than 12 (prod), starts with `change-me`, or is an unfilled `${...}` | Set both variables in `.env` (or the host's settings) to your own 12+ character values |
| `Variable SHOP_ADMIN_PASSWORD is required` from `docker compose` | The `:?` rule: the variable is not in the shell or in `.env` | Create `.env` next to `compose.yaml` |
| `.env` is ignored | It is in the wrong folder: compose reads the `.env` next to the compose file (or in the folder you run it from, with `--env-file`) | Put it in `lessons/46-deploy/solution/` |
| The new password does not work | The user table was filled on the first start; the hash is stored | Delete the volume (`down -v`) or the `shop-data` folder, start again. A real app needs a "change password" feature |
| The app uses 8080 although you set `PORT` | `SERVER_PORT` or `--server.port` is set somewhere stronger | Check the layers: command line, then environment, then files |
| Works with `java -jar`, fails in the container | A path or variable differs (`SHOP_DATA_DIR`), or the volume is missing | `docker compose logs`; check `/data` is the mounted volume |
| A secret is in `git log` | It was committed once | Change the secret now. Removing it from history is a second step, never the first |
| The hosted app is very slow on the first request | The free plan put it to sleep | That is the plan, not a bug. Lesson 47's health check does not prevent it |
| The data is gone after a redeploy on a platform | Ephemeral disk | Attach a persistent disk if the plan offers one, or move to a managed database |
| Login works over HTTP but you are on the public internet | No HTTPS | Stop. Put TLS in front (platform, proxy or tunnel) before sharing the address |
| `PORT` variable already exists on your PC and the app listens elsewhere | Some tools set `PORT` globally | `echo $PORT`; unset it, or run with `PORT=8080` |

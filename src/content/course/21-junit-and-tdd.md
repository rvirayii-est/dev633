## 1. Learning objectives
After this lesson you can:
- write a JUnit 5 test class using `@Test`, `@DisplayName`, `@BeforeEach`, `@Nested`, `assertEquals`, `assertTrue`, `assertThrows`, `assertAll`;
- lay a test out as **Arrange, Act, Assert** and give it a name that states the rule;
- turn a table of examples into a `@ParameterizedTest` and choose the **boundary** values;
- do **red, green, refactor** in small steps, and say why the test comes *first*;
- read a failing test (expected vs actual, line number) and tell a bad test from bad code.

## 2. Plain-English explanation
- **You have used tests for 20 lessons; now you write them.** A test is a small program that calls your code and checks the answer. Tests run in a second, so you can change code without fear: if you break something, a test turns red and tells you where.
- **What JUnit does.** It finds methods marked `@Test`, creates a **new object for each one** (so tests cannot affect each other), runs them, catches the failure of any assertion, and prints a report. `examples/MiniTestDemo.java` builds a 30-line version so you can see there is no magic.
- **Anatomy of a good test.**
  ```java
  @Test
  @DisplayName("exactly at the reorder level counts as LOW: order up to twice the level")
  void atTheLevelBringsTheShelfUpToTwiceTheLevel() {
      Product oil = product("Cooking Oil 1L", 10, 10);          // Arrange: set the scene
      int suggestion = ReorderAdvisor.suggestedQuantity(oil);   // Act: call the one thing you test
      assertEquals(10, suggestion);                             // Assert: expected first, actual second
  }
  ```
  A good test is **F.I.R.S.T.**: **F**ast, **I**ndependent (any order, alone), **R**epeatable (same result today and tomorrow: that is why we inject a `Clock`, lesson 20), **S**elf-checking (it says pass or fail; nobody reads printed output), **T**imely (written with the code, or before it).
- **Naming.** The name is documentation, and it is the first thing you read when the test fails. Say the rule in a sentence: `anEmptyShelfOrdersTwiceTheLevel`, not `test1` and not `testSuggestedQuantity`. Add `@DisplayName("...")` for a readable report. Keep **one idea per test**: when `aBrokenExpectation...` fails you know exactly which rule broke.
- **Assertions you need.**
  | Assertion | Use for |
  |---|---|
  | `assertEquals(expected, actual)` | the answer is exactly this (for `double` add a delta: `assertEquals(3.1, x, 0.001)`) |
  | `assertTrue` / `assertFalse` | a yes/no answer |
  | `assertThrows(X.class, () -> code)` | the code must refuse; it returns the exception so you can check its message |
  | `assertNull` / `assertNotNull` / `assertSame` | the absence of a value, or the very same object |
  | `assertAll(...)` | several checks on one result; **all** are reported, not just the first |
  | `fail("message")` | this branch must never run; also a placeholder for a test you have not written |
- **Setup and structure.** `@BeforeEach` runs before every test (a fresh shelf each time). `@Nested` groups tests by situation. `@TempDir` gives a throw-away folder (lesson 19). `@Disabled("reason")` skips a test: use it rarely and always with a reason; never as a way to hide a failure.
- **Parameterized tests.** When the *same* check applies to many examples, write it once and list the examples:
  ```java
  @ParameterizedTest(name = "{0} in stock, level {1} -> order {2}")
  @CsvSource({"12, 10, 0", "10, 10, 10", "4, 10, 16", "0, 10, 20"})
  void followsTheRule(int quantity, int level, int expected) { ... }
  ```
  `@ValueSource(ints = {0, -1})` for one argument; `@MethodSource("name")` when the examples are objects (lists, records). Each row is reported as its own test.
- **Which examples? The boundaries.** Bugs live at the edges: `>` instead of `>=`, off by one. For a rule that changes at 10, test 9 and 10; for "level 0 means not tracked", test level 0 and 1. A table with the typical case and the boundary on each side catches most mistakes.
- **TDD: test-driven development.** A loop of three small steps:
  1. **Red.** Write ONE test for ONE rule that does not work yet. Run it. It must fail, *for the right reason* (a message about your rule, not a typo). A test you never saw fail may be testing nothing.
  2. **Green.** Write the **least** code that makes it pass. Even `return 0;` is allowed if the next test will force something better. Run **all** tests.
  3. **Refactor.** Tidy names and duplication while every test stays green. Then the next rule.
  Why first? It forces you to decide what "correct" means before you code, it gives you a to-do list of small steps, and every line you write exists because a test demanded it. It does not mean "never think ahead": you still design; the test just checks the design as you go.
- **Check your tests: break the code on purpose.** Change `>` to `>=` in `ReorderAdvisor`. At least one test must go red. If none does, your tests have a hole. (Tools automate this; it is called mutation testing.)
- **What to test, what not to.** Test rules and edges: calculations, validation, decisions. Do not test the language (`list.add` adds) or trivial getters. Test through the **public** methods; if you feel the need to test a private method, it probably wants to be its own class. Coverage numbers (80%) measure which lines ran, not whether you checked anything; a test with no assertion gives 100% coverage and proves nothing.
- **A failing test is information.** Read it from the top: *Which test? What did it expect? What did it get? At which line?* Decide whether the code or the test is wrong. Never "fix" a test by copying the wrong answer into it.
- **Added to the app this lesson, test-first:** `ReorderAdvisor` (the buying rule below), `ReorderSuggestion` and `Inventory.reorderSuggestions()`. The rule: a product with reorder level 0 is not tracked (suggest 0); more than the level on the shelf is fine (0); otherwise order enough to bring the shelf up to **twice** the level. So cooking oil (4 in stock, level 10) gives 16, and sugar (0 in stock) gives 20.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `expected: <16> but was: <0>` | The code does not do it yet (red) | That is the point of step 1: now write the code |
| The test passes on the first run | It tests nothing, or the code already did it | Break the code on purpose; if the test stays green, strengthen it |
| Arguments swapped: "expected 4 but was 16" when the code is right | `assertEquals(actual, expected)` is the wrong way round | Expected first, actual second |
| `No ParameterResolver registered` / parameters not found | `@Test` used instead of `@ParameterizedTest` | Use `@ParameterizedTest` with a source annotation |
| `Could not find factory method [x] in class` | `@MethodSource("x")` names a method that is not `static` or has another name | Make the factory method `static` and spell the name exactly |
| Tests pass alone but fail together | Shared state: a field or static object changed by another test | Create what you need in `@BeforeEach`; never share mutable objects |
| A test fails only sometimes | It depends on the real time, random numbers, or file order | Inject a `Clock`, a seeded `Random`, a `@TempDir` |
| A huge test with ten asserts, and nobody knows what broke | Too much in one test | One rule per test; use `assertAll` only for facets of one result |
| You "fixed" a failing test by changing its expected value | You trusted the code over the specification | Decide from the rules which one is wrong, and say why |

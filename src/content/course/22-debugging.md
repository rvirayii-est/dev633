## 1. Learning objectives
After this lesson you can:
- read a **stack trace** and say what happened, where, and who called it;
- follow the debugging method: **reproduce, isolate, guess, check, fix, protect** (with a test);
- set a **breakpoint**, run to it, step through code and watch variables change, in your IDE;
- use **print debugging** (and know when it is the better tool);
- name what `NullPointerException`, `IndexOutOfBoundsException`, `NumberFormatException`, `ArithmeticException` and friends mean;
- fix a bug at its **cause**, not its symptom, and write the test that would have caught it.

## 2. Plain-English explanation
- **A bug is a difference between what you expect and what happens.** Debugging is finding *where* the two part ways. It is detective work, not luck: the code always does exactly what it says; the surprise is that what it says is not what you meant.
- **The method.**
  1. **Reproduce.** Make it fail every time, with the *smallest* input. "The report is wrong" is useless; "two prices, 3 and 4, give an average of 3.0" can be fixed. A failing test is the best reproduction: it is repeatable, shareable and permanent.
  2. **Isolate.** Narrow down *where*. Which test fails? Which method? Which line first has a wrong value? Halve the problem: does the first half of the data fail? the first half of the steps?
  3. **Guess (a hypothesis).** "Integer division is dropping the decimals." Make it a statement that can be proven wrong.
  4. **Check.** Look at the real value (debugger or print). If the guess is wrong, that is progress: cross it out and guess again. Change **one thing at a time**.
  5. **Fix the cause.** Not `if (answer == 3.0) answer = 3.5;`. Ask why the wrong value existed.
  6. **Protect.** Keep a test that fails without the fix. Run all tests: did the fix break something else?
- **Reading a stack trace.** When an exception is not caught, Java prints the list of method calls that were waiting. From `java.lang.IndexOutOfBoundsException: Index 3 out of bounds for length 3` (the starter's `CounterTest`):
  ```
  java.lang.IndexOutOfBoundsException: Index 3 out of bounds for length 3     <- 1. WHAT: the kind and the message
      at java.base/java.util.Objects.checkIndex(Objects.java:385)             <-    Java's own code: skip
      at java.base/java.util.ArrayList.get(ArrayList.java:427)                <-    skip
      at dev.javabybuilding.inventory.Counter.top(Counter.java:47)            <- 2. WHERE: the first line of YOUR code. Start here
      at dev.javabybuilding.inventory.CounterTest.topGives...(CounterTest.java:42)  <- 3. WHO CALLED: the test, line 42
  ```
  Read the message, then jump to the first line in your own package. Almost always the bug is on that line or a line just before it. If you see `Caused by:`, scroll to the last `Caused by`: that is the original problem. The newest call is at the top, the oldest at the bottom.
- **Exceptions and what they usually mean.**
  | Exception | Usually means |
  |---|---|
  | `NullPointerException` | you used something that is `null`. The message names it: `because "StackTraceDemo.nickname" is null` |
  | `IndexOutOfBoundsException` / `ArrayIndexOutOfBounds` | an index below 0 or at/above the size: **off by one** (valid indexes are 0 to size - 1) |
  | `NumberFormatException` | text that is not a number was parsed (`"x3"`, `"12.5"` for an int, an empty string) |
  | `ArithmeticException: / by zero` | integer division by 0 (doubles give `Infinity` instead) |
  | `ClassCastException` | a cast to the wrong type |
  | `UnsupportedOperationException` | you changed a list made by `List.of` or `List.copyOf` |
  | `ConcurrentModificationException` | a list was changed while a loop walked it |
  | `StackOverflowError` | a method calls itself forever (recursion without an end) |
  | `ArithmeticException: Non-terminating decimal expansion` | `BigDecimal.divide` without a rounding rule (lesson 20) |
- **The usual suspects** (what the six exercises plant): integer division (`5 / 2` is 2), `==` on Strings (asks "same object?", not "same letters?"), `<` where `<=` was meant, a loop that starts at 1 or stops one early, a plus sign where a minus belongs, and a sign flipped in a `switch`.
- **The debugger.** It runs your program but lets you pause it. Everything below works in IntelliJ IDEA Community and in VS Code with the Java extension.
  | Action | What it does |
  |---|---|
  | **Breakpoint** (click left of a line number) | the program stops *before* running that line |
  | **Debug** (not Run) | starts the program, or one test, with breakpoints active (click the bug icon / "Debug Test") |
  | **Step over** (F8 / F10) | run this line, stop at the next one in the same method |
  | **Step into** (F7 / F11) | go inside the method this line calls |
  | **Step out** (Shift+F8 / Shift+F11) | finish this method, stop in its caller |
  | **Resume** (F9 / F5) | run until the next breakpoint |
  | **Variables / Watch** | see every variable's value now; add an expression like `total / prices.size()` and watch it |
  | **Call stack** panel | the same list as a stack trace, but you can click a frame to see *its* variables |
  | **Conditional breakpoint** (right-click the red dot) | stops only when e.g. `i == 99`, instead of 100 times |
  A typical session: set a breakpoint on the first line of the method the stack trace names, Debug the failing test, step line by line, and compare each variable with what you expected. The **first line where a value is wrong** is the bug, or just above it.
- **Print debugging.** `System.out.println("total=" + total + " size=" + size)` is a legitimate tool: quick, works anywhere, shows many steps at once. Print *labels with values*. Remove the prints afterwards. (Lesson 24 replaces prints with real logging.) Use the debugger when you need to look around; prints when you need to watch a loop.
- **Habits that save hours.** Read the *whole* message. Change one thing at a time. Don't trust a comment; trust what runs. Explain the problem aloud to a rubber duck or a friend ("rubber-duck debugging"): the explanation often reveals the bug. Take a break. Look at what changed since it last worked (`git diff`, and lesson 23's `git bisect` idea). Never "fix" a bug you cannot explain: it will come back.
- **A good bug report** (for a teammate, or yourself next week): *What I did, what I expected, what happened (paste the message), the smallest input that shows it, the version/commit.* A failing test is the best one.
- **New in the app:** `Inventory.audit()`, a health check that compares every shelf quantity with what the stock log adds up to. It must always return an empty list; if it does not, there is a bug (or an edited file) and the message names the product. Using such a self-check is a classic debugging aid.

## 4. Step-by-step: the bug hunt in the shop
The `starter` is lesson 21's finished app with **six bugs planted** (one per problem below). The tests are the same good tests you already know, so the failing ones are your bug reports. You will fix the app without writing new features. Work on **one bug at a time** and run the tests after each fix.
1. Run `../../../mvnw test`. Read the summary: 239 tests, 14 failures, 8 errors. Do not panic; there are only six causes. Group the failures by area (stock status, totals, movement log, Counter, name comparison, reorder rule).
2. **Bug 1: a stack trace.** `CounterTest.topGives...` is an *error* with an `IndexOutOfBoundsException`. Read the trace as described above: find the first `dev.javabybuilding` line, open it, work out why the index can equal the size. Fix it.
3. **Bug 2: expected 2000.80 but was 3001.20** (`SaleTest`, `InventoryTest`, `SalesReportTest`). Set a breakpoint in `Sale.total()`, Debug the failing `SaleTest` test, and look at `subtotal()` and `discountAmount()`. Is `total` what the receipt rule says (subtotal **minus** discount)? Fix it.
4. **Bug 3: `expected: <LOW> but was: <OK>`** (`StockCheckerTest`, `ProductTest.statusFollowsTheReorderLevel`). The test name says "at or below". Which comparison operator is wrong? Fix it, then add nothing: the test already protects it.
5. **Bug 4: `expected: <-5> but was: <5>`** (`StockMovementTest`). A *sold* movement must reduce the shelf. Find the one `switch` that decides the sign. This bug breaks the stock log, so `Inventory.audit()` and the file loader complain too: one cause, many failing tests. Fix the cause and many failures disappear together; this is why you fix **one bug at a time**.
6. **Bug 5: `TextUtilTest.sameNameIgnoresCapitalsAndExtraSpaces`.** Two names that look the same are reported as different. Use **print debugging** or the Evaluate-expression window: what does `TextUtil.clean(a) == TextUtil.clean(b)` give, and what does `.equals` give?
7. **Bug 6: `ReorderAdvisorTest` rows `[3]` and `[9]`.** The `@ParameterizedTest` display names show *which rows* fail: `10 in stock, reorder level 10 -> order 10` and `3 in stock, reorder level 3 -> order 3`. What do both rows have in common? Boundary! Fix it.
8. Run all tests: green. Run `git diff --no-index ../21-junit-and-tdd/solution/src/main/java/dev/javabybuilding/inventory starter/src/main/java/dev/javabybuilding/inventory` from this lesson folder: your fixes should be the only differences besides `Main.java`'s version line and the new `audit()`.
9. **Write a regression test** for the one bug you think was easiest to introduce by accident. Does it fail if you put the bug back? (Do it: put the bug back, watch it fail, fix it again.)

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| You changed three things and it works, but you do not know which fixed it | Several changes at once | Undo, then change one thing at a time |
| The breakpoint is grey / never hit | You pressed Run instead of Debug, or the line is never executed | Use Debug; put the breakpoint on a line that really runs (not a comment or a declaration) |
| The debugger stops in Java's own code | You stepped *into* a library method | Step out (Shift+F8) and use step over next time |
| `NullPointerException` message mentions `<local4>` | The code was compiled without variable names | Read the line number; or compile with `-g` (Maven and IDEs do) |
| "It worked on my machine" | A hidden difference: data, time, folder, Java version | Reproduce with a test using a fixed Clock and a `@TempDir` |
| The print statements are everywhere and the output is a flood | Printing without labels or a plan | Print `label=value` only around the suspect, then delete them |
| The bug "moved" after a fix | You fixed a symptom | Ask why the wrong value existed in the first place |
| The test failed, so you changed the test | You trusted the code over the specification | Decide from the rules which is wrong |
| A fix breaks another test | The other test relied on the buggy behaviour, or the fix is too broad | Read both tests; one of them describes the rule wrongly |

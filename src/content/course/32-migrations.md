## 2. Plain-English explanation
Software lives for years; so does its data. In month 3 the shop wants customers' e-mail addresses. In month 5 it wants to hide products without deleting them. Each change touches the **design** of the database (tables and columns), while the sales already recorded must stay. How do you change the design of a database that is running on a laptop in the shop, another laptop at the owner's house, a test machine and (soon) a server, so that all of them end up identical?

**Wrong way:** type the `ALTER TABLE` by hand on each machine. Somebody forgets one. Now the app works on three machines and crashes on the fourth with `Column "EMAIL" not found`. Nobody remembers which machine has which design. This is **schema drift**.

**Right way: migrations.** Every change is a small SQL **file with a number**, kept in Git next to the code. The app (or a tool) applies the files **in order**, and each database remembers which ones it already has.

### The shop's migrations
In `src/main/resources/db/migration/`:
| File | What it does |
|---|---|
| `V1__create_shop_tables.sql` | the design from lesson 28 (5 tables, rules, indexes) |
| `V2__add_customer_email.sql` | `ALTER TABLE customer ADD COLUMN email VARCHAR(100)`: optional |
| `V3__add_product_active_flag.sql` | `ALTER TABLE product ADD COLUMN active BOOLEAN NOT NULL DEFAULT TRUE` |
| `index.txt` | the list of file names (a classpath cannot always be searched; a test checks the list is complete) |

The file name rule: `V` + version number + **two** underscores + a description (single underscores for spaces) + `.sql`.

Adding a column to a table that **already has rows** is where beginners get hurt. The new column needs a value for every old row:
- make it **optional** (no `NOT NULL`): old rows get `NULL`. Do this for `email`.
```sql
ALTER TABLE customer ADD COLUMN email VARCHAR(100);
SELECT name, email FROM customer ORDER BY id;
```
```text
name        | email
------------+------
Ana Reyes   | NULL
Ben Santos  | NULL
Carla Dizon | NULL
(3 rows)
```
- or give it a **`DEFAULT`**: old rows get the default. Do this for `active`.
```sql
ALTER TABLE product ADD COLUMN active BOOLEAN NOT NULL DEFAULT TRUE;
SELECT name, quantity, active FROM product ORDER BY id;
```
```text
name            | quantity | active
----------------+----------+-------
Rice 25kg       | 17       | TRUE
Cooking Oil 1L  | 12       | TRUE
Sugar 1kg       | 4        | TRUE
Sardines 155g   | 30       | TRUE
Soy Sauce 500ml | 0        | TRUE
Instant Noodles | 5        | TRUE
(6 rows)
```
`NOT NULL` without a `DEFAULT` on a table with rows fails: the database cannot invent values.

### The golden rule: never edit a migration that has been applied
Once `V2` ran anywhere, it is history. If it was wrong, you do **not** fix the file: you add `V4` that corrects it. Otherwise the machines that already ran the old `V2` differ from the ones that run the edited one, which is drift again, by a different door. To catch this, the runner stores a **checksum** (a number computed from the file's text; here CRC32). Edit the file and the checksum changes, and the app refuses to start:
`Migration V2 (add customer email) was changed after it was applied. Put the file back as it was and write a NEW migration for the change.`
The checksum ignores Windows-versus-Linux line endings (`\r\n` against `\n`), or every Windows student would trip over it.

### The runner, step by step (`Migrator`)
1. Create the **history table** if missing: `schema_version(version, description, checksum, applied_at)`.
2. Read what the database has already had.
3. **Check**: every applied version must still exist with the same checksum; the database must not be newer than the app (`The database is at version 5 but this app only knows versions up to 3`).
4. For each migration not yet applied, **in version order**: run its script, then record it in `schema_version`, together in one transaction (lesson 31).
5. If a script fails, stop, name the version, and leave later ones unapplied. Fix the file (it never succeeded, so it is not history yet) and run again: the runner carries on from there.

```sql
CREATE TABLE schema_version (version INT PRIMARY KEY, description VARCHAR(200) NOT NULL, checksum BIGINT NOT NULL, applied_at TIMESTAMP NOT NULL);
INSERT INTO schema_version VALUES (1, 'create shop tables', 1234567890, TIMESTAMP '2026-03-01 09:30:00');
SELECT version, description, applied_at FROM schema_version;
```
```text
version | description        | applied_at
--------+--------------------+--------------------
1       | create shop tables | 2026-03-01 09:30:00
(1 row)
```
(That is the table `Migrator` keeps. The checksum above is made up for the demo.)

Two limits to know. **DDL** (`CREATE`/`ALTER TABLE`) commits by itself in H2 and MySQL, so a script that fails *half way* may leave its first statements applied: keep each migration small (one change per file). PostgreSQL can roll DDL back. And the runner assumes one app starting at a time; real tools take a lock on the history table so two servers do not migrate at once.

### Flyway: the professional equivalent
You wrote the idea by hand to understand it. In real projects you use a tested tool, and **Flyway** is the most common in the Java world. It uses the **same file naming** (`V1__name.sql`), the same idea of a history table (`flyway_schema_history`) and checksums. What it adds:

| This lesson's `Migrator` | Flyway |
|---|---|
| `index.txt` lists the files | scans the folder (`db/migration`) for you |
| one history table, CRC32 checksums | same idea, plus who applied it and how long it took |
| `migrate()` | `flyway.migrate()`; also `info`, `validate`, `baseline` (adopt an existing database), `repair` |
| no locking | locks the history table so two servers cannot migrate together |
| H2 only, tested here | dozens of databases, dialect-aware |
| versioned only | also **repeatable** migrations (`R__refresh_views.sql`, re-run when they change) |
| — | with Spring Boot (lesson 36 on) it runs **automatically at start-up** when `flyway-core` is on the class path |

So the day you move to Spring Boot you delete `Migrator`, add one dependency, keep your `db/migration` folder as it is, and the history keeps working. Liquibase is the other well-known tool (it describes changes in XML/YAML/JSON instead of plain SQL).

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `Migration V2 ... was changed after it was applied` | You edited a migration that already ran | Restore the file (`git checkout`) and put the change in a new `V<next>` file. On a throw-away local database you may delete `shop-data/` and start again |
| `The database is at version 4 but this app only knows versions up to 3` | An old app on a newer database | Run the newer app, or use another folder |
| `Migration V3 is missing (found V4 instead)` | A file is missing, or two people numbered differently | Restore the file; renumber a duplicate before merging |
| `Not a migration file name` | The name is not `V<n>__<description>.sql` (one underscore, lower-case v, no number) | Fix the name: two underscores after the number |
| `Migration file not found: /db/migration/V4__x.sql` | The file is listed in `index.txt` but not in the folder (or not rebuilt) | Check the name and run the build again |
| `MigrationTest.indexTxtListsEveryMigrationFile...` fails | You added a `V*.sql` file and forgot `index.txt` | Add its name to `index.txt` |
| `NULL not allowed for column "ACTIVE"` while migrating | `ADD COLUMN ... NOT NULL` with no `DEFAULT` on a table with rows | Add a `DEFAULT`, or make the column optional and fill it later |
| Half the migration is applied and the next run fails with "already exists" | DDL cannot be rolled back in H2; the script failed half way | Fix by hand once (drop what it created, or delete the throw-away database), and keep migrations to one change |
| The checksum differs between two students' computers | Line endings or an editor adding a final newline | The checksum normalises `\r\n`; do not let tools reformat applied files |
| Tests leave `shop-data` in the repo | A test used a real folder | Tests use `@TempDir`; check `git status` |

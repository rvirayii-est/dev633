## 1. Learning objectives
After this lesson you can:

- **write** the rules table in `SecurityConfig`: specific rules first, a safe catch-all last, because **the first matching rule decides**;
- **return** `403 Forbidden` in the same JSON shape as every other error, and tell it apart from `401`;
- **add** a `role` column to a table that already has rows with a Flyway migration (V5) without locking anyone out;
- **test** the rules three ways: a matrix over the real database, a fast slice with `@WithMockUser`, and a real HTTP login.

## 2. Plain-English explanation
Lesson 41 answered "who are you?" Now: **"what may you do?"** In a real shop the person at the till should sell and look things up, but should not delete products, change prices or read the sales report. The owner can do all of it. Two jobs, two **roles**:

| | ADMIN | CASHIER |
|---|---|---|
| read products and sales (`GET /products`, `GET /sales`...) | yes | yes |
| record a sale (`POST /sales`) | yes | yes |
| create, change, delete a product; receive a delivery (`POST/PUT/DELETE /products...`) | yes | **no** |
| read reports (`GET /reports/...`) | yes | **no** |
| `GET /me`, `GET /hello` | yes | yes |

A user that is signed in but not allowed gets **`403 Forbidden`**: "I know who you are, and the answer is no". A stranger still gets `401`.

### Least privilege, and a safe default
Two habits that matter more than any syntax:
1. **Least privilege.** Start from "nobody may" and add exactly what each role needs. A cashier whose password leaks should be able to do a cashier's harm, not an owner's.
2. **Deny by default.** The last rule, `anyRequest().hasRole("ADMIN")`, covers everything not listed. When you add a new endpoint and forget the rules table, it is closed to cashiers until someone decides. (For an unknown path an admin gets `404` and a cashier `403`; see the test `aPathNobodyListedIsClosedToTheCashier...`.) The opposite habit, "open unless listed", turns every forgotten line into a hole.

### The rules table
Spring Security reads the rules **top to bottom and stops at the first match**:
```java
.authorizeHttpRequests(rules -> rules
    .requestMatchers("/hello", "/error").permitAll()
    .requestMatchers("/me").authenticated()
    .requestMatchers(HttpMethod.GET, "/products", "/products/*", "/sales", "/sales/*").hasAnyRole("ADMIN", "CASHIER")
    .requestMatchers(HttpMethod.POST, "/sales").hasAnyRole("ADMIN", "CASHIER")
    .requestMatchers("/products", "/products/**", "/reports/**").hasRole("ADMIN")
    .anyRequest().hasRole("ADMIN"));
```
Read it as a story: "GET on products is for both roles; **but** any other method on `/products...` (POST, PUT, DELETE: the `/products/**` rule) is for admins". The order is the whole trick: if the `/products/**` line came first, cashiers could not even read products. `RoleMatrix.java` (examples) prints this table and shows the mistake.

A **role** is stored as an *authority* with the prefix `ROLE_` (`ROLE_ADMIN`). `hasRole("ADMIN")` adds the prefix for you; `.roles("ADMIN")` when building a user does too. Mixing the two styles (`hasAuthority("ADMIN")` against `ROLE_ADMIN`) is the most common reason for an unexpected `403`.

### Why URL rules and not annotations
Spring can also guard a method with `@PreAuthorize("hasRole('ADMIN')")`. We keep **all the rules in one file** because a reviewer can read the whole policy in one screen, and because a refused request is stopped *before* it reaches the controller, so the `ApiExceptionHandler` of lesson 39 never turns an `AccessDeniedException` into a confusing `500`. Annotations are a good second layer for rules about *data* ("only the owner of this record"), which a URL cannot express.

### A migration on a table that has rows (V5)
The table `app_user` from lesson 41 may already hold users. Adding a `NOT NULL` column without a default would fail, so V5 does it in two steps:
```sql
ALTER TABLE app_user ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT 'CASHIER';   -- everybody who exists becomes the least powerful role
UPDATE app_user SET role = 'ADMIN' WHERE username = 'admin';                    -- then the admin is promoted
```
`UserRoleMigrationTest` proves it: it migrates to version 4, inserts three users, migrates to the latest version and checks `admin` is `ADMIN` and the others `CASHIER`. **Test a migration against data, not only against an empty database.**

## 5. Practical exercises
In `exercises/` (`RoleDrills.java`; tests in `Exercises42Test.java`): a tiny rules engine, so "the first match decides" becomes something you wrote.
1. `matches(pattern, path)`: `*` is one path part, `**` is the rest.
2. `rolesFromAuthorities(List.of("ROLE_ADMIN", "SCOPE_read"))` gives `{"ADMIN"}`.
3. `allowed(rules, method, path, roles)`: first match decides, no match means no.
4. `explain(...)`: `ALLOWED by rule 2`, `DENIED by rule 3`, `DENIED: no rule matches`.

*Stretch:* make `matches` case-insensitive for the method names and ignore a trailing `/`. Then check what Spring does for `GET /products/` (a trailing slash) in your running app. Is it the same as `GET /products`?

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| A cashier can delete products | A broad rule (or `authenticated()`) comes **before** the `ADMIN` rule | Specific rules first; the catch-all last. Rerun `RolesTest` |
| A cashier gets `403` on `GET /products` | The `ADMIN` rule for `/products/**` is above the `GET` rule | Reorder: the first match wins |
| Everyone gets `403`, even the admin | `hasAuthority("ADMIN")` against the authority `ROLE_ADMIN` (or the other way round) | `hasRole("ADMIN")` with `.roles("ADMIN")`; `hasAuthority("ROLE_ADMIN")` with `.authorities("ROLE_ADMIN")` |
| `401` instead of `403` for a user who is signed in | The credentials were wrong, or the request raced the seeder in the first second after start-up | Check the password; wait for start-up to finish |
| `GET /products/Rice 25kg` is `404` or `400` in `curl` | The space in the URL | `curl localhost:8080/products/Rice%2025kg` |
| `IllegalArgumentException: No enum constant AppRole.MANAGER` at login | The database holds a role the code does not know | Fix the row, or add the role to the enum |
| The migration fails with `NULL not allowed for column "ROLE"` | `NOT NULL` without a `DEFAULT` on a table that has rows | Add the column with a default (V5), then update |
| A `@WebMvcTest` answers `401` or `403` to everything | It uses Spring's default security, not ours | `@Import(SecurityConfig.class)` and `@WithMockUser(roles = "...")` |
| A test works alone and fails with the others | `RolesTest` records a sale, and another test expects an empty shop | Give it its own in-memory database (`mvc-roles`) |
| `AccessDeniedException` turns into `500` | A `@PreAuthorize` inside a controller is caught by the catch-all `@ExceptionHandler(Exception.class)` | Keep access rules in the filter chain, or add a handler that rethrows `AccessDeniedException` |

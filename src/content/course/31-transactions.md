## 2. Plain-English explanation
Recording a sale is **three** changes: (1) take the units off the shelf (`product.quantity`), (2) store the receipt (`sale`, `sale_line`, maybe a new `customer`), (3) write the stock log (`stock_movement`). In lesson 30 each change was saved the moment it ran (**auto-commit**, JDBC's default). If step 3 fails (disk full, a rule refuses the row, the power goes), the first two stay saved: five sacks of rice have left the shelf and there is a receipt, but the log says nothing happened. The records now disagree, and `audit()` reports it forever.

A **transaction** groups statements into one unit:
- `commit()` = "all of it counts, save it";
- `rollback()` = "none of it counts, undo everything since the start".

Think of a bank transfer: taking 500 from one account and adding 500 to the other must never stop half way.

### ACID in four short promises
| Letter | Promise | In the shop |
|---|---|---|
| **A**tomic | all or nothing | shelf, receipt and log change together or not at all |
| **C**onsistent | the rules always hold afterwards (`CHECK`, `FOREIGN KEY`, `UNIQUE`: lesson 28) | quantity never goes negative |
| **I**solated | while you work, others do not see your half-finished changes | Ben never sees Ana's unfinished sale |
| **D**urable | after `commit()` returns, the data survives a crash | the sale is still there after the power cut |

### The JDBC recipe
```java
connection.setAutoCommit(false);          // start: statements now wait for the verdict
try {
    // ... several statements ...
    connection.commit();                  // success: save all of it at once
} catch (RuntimeException | SQLException e) {
    connection.rollback();                // failure: undo all of it
    throw e;                              // and still tell the caller
} finally {
    connection.setAutoCommit(true);       // always go back to normal
}
```
`examples/AllOrNothing.java` runs the same broken sale twice, once with auto-commit and once like this.

### Where does the code go?
Not in the repositories: they do **one** thing each (`products.update`, `sales.add`). Not in the menu either. The *service* knows which steps belong together, so `ShopService.sell` says: "run these three steps in a transaction". Two small pieces make that possible:

- `Transactor`: an interface with one method, `inTransaction(work)`. `ShopService` depends on this interface, not on JDBC.
- `Database implements Transactor`: the JDBC recipe above. If a transaction is already running, the work **joins** it (the outermost call decides). So `importFrom` can call `add` methods that start their own, with no harm.
- `Transactor.NONE`: just runs the work. In-memory repositories have nothing to undo, so the old four-argument `ShopService` constructor uses it.

```java
Sale sale = transactor.inTransaction(() -> {
    Product product = getProduct(name);
    product.sell(amount);                    // fails first if there is not enough stock
    products.update(product);                // step 1
    Sale stored = sales.add(draft);          // step 2
    movements.add(soldMovement);             // step 3
    return stored;
});
customer.addPurchase(sale.total());          // only after the commit: points for sales that really happened
```
Anything that is not database state (the `Customer` object's points, the log message) is done **after** the commit. A rollback cannot un-add points on a Java object.

### Isolation and the lost update
Run `examples/TwoCashiers.java`. Two cashiers use two connections.
1. **Isolation.** Until Ana commits, Ben still sees the old quantity. (H2's default level is *read committed*: you see only committed data.)
2. **Lost update.** Both read "3 sacks left", both sell 3, each writes `3 - 3 = 0`: 6 sacks sold, 3 in stock. Each cashier's transaction was fine on its own; together they oversold.
3. **The cure.** Let the database check and change in **one** statement: `UPDATE product SET quantity = quantity - ? WHERE name = ? AND quantity >= ?`. If it changes 0 rows, the stock was too low. Other cures: `SELECT ... FOR UPDATE` (lock the row while you work), or a version column. Our console app has one cashier and one connection, so `ShopService` keeps the simple read-then-write and says so (`shortcut`). The REST API in M6 will have many users at once, and then this matters.

### What a transaction does *not* do
- It does not fix wrong code: if you commit nonsense, it is saved reliably.
- It keeps **database** state, not Java objects.
- **DDL** (`CREATE TABLE`, `ALTER TABLE`) is different between databases: H2 and MySQL commit at once and cannot roll it back, PostgreSQL can. Lesson 32 relies on this.
- Keep transactions **short**: they hold locks. Never wait for a person's keyboard input inside one.
- On PostgreSQL and MySQL the recipe and the SQL are the same; defaults differ (MySQL's InnoDB is *repeatable read*, PostgreSQL's is *read committed*).

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| Nothing is saved after the work "succeeded" | `setAutoCommit(false)` but no `commit()` | `commit()` at the end of the work; check the `finally` |
| A failed sale still changed the shelf | The three steps ran without a transaction (`Transactor.NONE`), or auto-commit was left on | Pass the `Database` as the transactor; check `connection.getAutoCommit()` |
| Everything works but later statements are never saved | The connection stayed in manual mode after an error | `finally { connection.setAutoCommit(true); }` |
| `rollback()` did not undo a table you created | DDL commits by itself in H2 and MySQL | Keep DDL out of transactions (lesson 32), or use PostgreSQL |
| Points were added although the sale failed | `addPurchase` ran inside the work, before the commit | Do non-database work after the commit |
| Nested `inTransaction` committed too early | The inner call started its own transaction instead of joining | The outermost call must be the only one that commits (see `Database.inTransaction`) |
| `Timeout trying to lock table` | A long transaction holds locks | Keep transactions short; never wait for a person inside one |
| Two cashiers oversold | Read-then-write with no guard | Guarded `UPDATE ... AND quantity >= ?`, `FOR UPDATE`, or a version column |
| Swallowed exception hides the failure | `catch (Exception e) {}` around the work | Roll back and rethrow, never swallow |

## 2. Plain-English explanation
In lesson 29 `ProductDao` held the JDBC code. If the menu called `ProductDao` directly, the whole app would know about SQL: to test the rules you would need a database; to keep products in a file instead you would edit every caller.

A **repository** is an object that looks like a **collection** of your domain objects ("the products") and hides where they really live. You `add`, `findByName`, `findAll` and `update`; whether that means a SQL statement, a line in a CSV file or an entry in a list is the repository's secret. The rest of the app depends only on the **interface**.

> **DAO or repository?** A DAO is organised around *tables* ("the SQL for product"). A repository is organised around the *domain* ("the products, as a collection"). In small apps they look alike, and people mix the words. What matters: the app depends on an interface.

### The shop's repositories
| Interface | Implementations | Job |
|---|---|---|
| `ProductRepository` | `JdbcProductRepository` (lesson 29's DAO, renamed), `FileProductRepository` (reads and writes `products.csv`, the same format as `DataStore`), `InMemoryProductRepository` | products |
| `SaleRepository` | `JdbcSaleRepository`, `InMemorySaleRepository` | sales and their lines (and the customer rows) |
| `StockMovementRepository` | `JdbcStockMovementRepository`, `InMemoryStockMovementRepository` | the stock log |

Details that make the implementations interchangeable:
- **Copies, not the real thing.** A database gives you a *new* `Product` object each time. Change it and nothing is stored until you call `update(product)`. `InMemoryProductRepository` copies on purpose so tests do not pass by accident of sharing one object.
- **Same errors.** A duplicate name is an `InvalidInputException` with the same message in all three. An unknown product to `update` is an `UnknownProductException`. Callers never see `SQLException` or `IOException`.
- **A sale is a draft until it is stored.** `SaleRepository.add(draft)` takes a `Sale` whose number is ignored and returns the stored sale with the number the database gave it (`RETURN_GENERATED_KEYS`, in `JdbcSaleRepository`). `Sale.withNumber` makes the copy.
- **Points are not stored.** `JdbcSaleRepository.findAll` rebuilds each `Customer` (one object per name and phone) and replays the points from the sales, the same choice `DataStore` made.

### Contract tests: one test, every implementation
How do you know `FileProductRepository` really behaves like `JdbcProductRepository`? Write the rules once, as an abstract test class, and make each implementation pass them:

```java
abstract class ProductRepositoryContract {
    abstract ProductRepository create();      // each subclass says how to make a fresh one
    @Test void aSavedProductCanBeFoundAgain() { ... }
    @Test void theSameNameTwiceIsRefused()   { ... }
}
class JdbcProductRepositoryTest extends ProductRepositoryContract { ... create() { return new JdbcProductRepository(db); } }
class FileProductRepositoryTest extends ProductRepositoryContract { ... }
```
JUnit runs the inherited tests once per subclass. The contract is the *specification* of the interface; a new implementation (say PostgreSQL) must pass it before the app may use it. Each subclass can add tests for what only it can do (the database refuses a sale line for an unknown product).

### The shop's rules in a service
`ShopService` is lesson 15's `Inventory` rewritten on top of the three interfaces: `addProduct`, `receive`, `sell`, reports. It has no `Connection`, no `Path`, no SQL. `Shop` is the small interface that both `Inventory` and `ShopService` implement; `Menu` and `Main` were changed to depend on `Shop`, so **the same console app runs on either**. One test (`MenuOnShopServiceTest`) types the same keystrokes into both and checks the screens are identical. Another contract test (`ShopServiceContract`) runs the same business steps on `Inventory` and on a `ShopService` and compares reports, totals, the stock log and the audit.

Two small changes were needed in old code. `Menu` printed `product.getQuantity()` after a receive; with a database that object is a stale copy, so it now asks `shop.quantityOf(name)`. And `ProductDao` lost its `count()`: the interface has `findAll`.

### Where is the data on the first run?
`ShopService.importFrom(Inventory)` copies products, sales and the stock log into the repositories: used to start a database from the sample shop, and (lesson 32) from the CSV files of lesson 19. Nothing is invented: the stock log you had is the stock log you get.

### The weak spot
Read `ShopService.sell`. It does three separate things: (1) update the product's quantity, (2) store the sale, (3) log the stock movement. What if step 2 fails (disk full, a rule of the schema refuses the row)? The stock is already gone but there is no sale: money and stock disagree and `audit()` complains. Lesson 31 fixes this with **transactions**: all three steps succeed together or none happens.

### Why bother? Four payoffs
1. **Testing:** the rules of the shop run in milliseconds against `InMemory…` repositories.
2. **Swapping:** moving from CSV to a database (this lesson) or from H2 to PostgreSQL (one new class, no change in `ShopService`).
3. **Reading:** `ShopService` is about the shop, not about `PreparedStatement`.
4. **Later:** Spring Data (lesson 38) generates repositories for you from an interface. You will recognise the idea at once.

The price: more files, and a promise that implementations behave alike. The contract test keeps the promise.

### What was added to the app
`ProductRepository`, `SaleRepository`, `StockMovementRepository`; `Jdbc…` ×3, `InMemory…` ×3, `FileProductRepository`; `Shop`; `ShopService`; `Sale.withNumber`. Removed: `ProductDao` (it became `JdbcProductRepository`). `Menu` and `Main` now depend on `Shop`. The app still starts from CSV files; lesson 32 switches it to the database.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| A test passes with `InMemory…` and fails with `Jdbc…` | The implementations do not behave alike (often: sharing one object instead of copying) | The contract test found a bug. Fix the implementation, not the test |
| `Unknown product` when selling right after `addProduct` | A different repository object (or a different database name) was used for add and sell | Create the repositories once and give the same ones to `ShopService` |
| Quantity does not change on screen | You changed the `Product` copy and forgot `products.update(product)` | Call `update` after every change |
| `ShopService` imports `java.sql` | JDBC leaked out of the repository | Only `Jdbc…` classes and `Database` may import `java.sql` |
| Duplicate-name error has a different message in the file version | Each implementation invented its own text | Throw the shared `InvalidInputException` with the same text; the contract compares it |
| The sale number is 0 after `add` | You used the draft instead of the sale `add` returned | `Sale stored = sales.add(draft);` use `stored` |
| `Referential integrity constraint violation` while importing | Sales imported before the products they mention | Import products first |
| Stock went down but no sale exists | `sell` failed after step 1 | This is the lesson 31 problem: use a transaction |
| Everything is an interface now, even a class with one implementation | Over-engineering | Add an interface when you have (or clearly will have) a second implementation or a test double; `Shop` and the repositories qualify |

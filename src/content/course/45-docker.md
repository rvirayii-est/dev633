## 2. Plain-English explanation
Your API runs on your PC because your PC has Java 21, the right folder, the right settings. A server has none of that. **Docker** packages the app *with* its Java and its settings, so it runs the same on your laptop, a classmate's laptop, a CI machine and a server.

| Word | Meaning | Everyday picture |
|---|---|---|
| **image** | A read-only package: an operating system's files, Java, your jar, how to start it | A recipe *and* all the ingredients, sealed |
| **container** | A running copy of an image, isolated from the rest of the machine | One dish cooked from that sealed box |
| **Dockerfile** | The instructions that build an image | The recipe |
| **registry** | A server that stores images (Docker Hub, GitHub Container Registry...) | A shelf to share boxes |
| **volume** | A folder that lives outside the container, so data survives | A pantry that stays when the dish is eaten |
| **Compose** | A file that describes one or more containers and starts them together | The order for a whole meal |

A container is *not* a virtual machine: it shares the host's operating-system kernel, so it starts in a second and uses little memory. It is also *not* a safe place for secrets: anything inside an image can be read by anyone who has the image.

### The Dockerfile, line by line (`solution/Dockerfile`)
**Two stages.** Building a jar needs the JDK and Maven (hundreds of MB). Running it needs only a JRE. A *multi-stage* build uses the big one to build and throws it away:
```dockerfile
FROM eclipse-temurin:21-jdk AS build          # stage 1: JDK, named "build"
...
FROM eclipse-temurin:21-jre AS runtime        # stage 2: only a JRE
COPY --from=build /workspace/shop-api.jar /app/shop-api.jar   # take ONE file from stage 1
```
Only stage 2 becomes the image. The compilers, the Maven cache and the source code stay behind, so the image is smaller and has less in it to attack. **Pin the tag** (`21-jre`, never `latest`): `latest` changes under you and a build that worked yesterday breaks today.

**The cache-friendly order.** Docker keeps each instruction as a *layer* and reuses it while that instruction and everything before it are unchanged. So:
```dockerfile
COPY mvnw pom.xml ./                               # 1. only the files that say WHICH libraries
COPY .mvn .mvn
COPY ${LESSON}/pom.xml ${LESSON}/pom.xml
RUN ... ./mvnw -B -q -f ${LESSON}/pom.xml dependency:go-offline     # 2. download them (slow, cached)
COPY ${LESSON}/src ${LESSON}/src                   # 3. THEN your code (changes all the time)
RUN ./mvnw -B -q -f ${LESSON}/pom.xml package -DskipTests           # 4. build the jar
```
Edit a Java file: steps 1 and 2 are cached, only 3 and 4 run. Edit a `pom.xml`: from step 1 on everything runs again. `LayerCacheDemo.java` replays this with numbers. (`-DskipTests` because CI already ran the tests; an image build is for packaging.)

**Why the context is the repository root.** `docker build` sends a folder (the *context*) to Docker, and `COPY` can only see inside it. This module's `pom.xml` names the course's root `pom.xml` as its *parent*, so the build must see the root. In a project of your own with one `pom.xml`, the context is the project folder and the first lines are simpler. `sed -i 's/\r$//' mvnw` removes Windows line endings, which would otherwise break the script inside Linux.

**Not root.**
```dockerfile
RUN groupadd --system shop && useradd --system --gid shop --home-dir /app shop && mkdir -p /data && chown shop:shop /data
USER shop
```
By default a container runs as *root*. If someone breaks into the app, they would be root inside the container. A system user with no shell and one writable folder (`/data`) limits that.

**Start-up.**
```dockerfile
ENV SHOP_DATA_DIR=/data
VOLUME /data
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "/app/shop-api.jar"]
```
- `ENV SHOP_DATA_DIR=/data`: Spring Boot turns the environment variable `SHOP_DATA_DIR` into the property `shop.data-dir`, so the database file goes to `/data/shop.mv.db`. No code change.
- `VOLUME /data` marks it as data that must outlive the container.
- `EXPOSE 8080` documents the port (it does not publish it; `-p` or compose does).
- The `ENTRYPOINT` is the **exec form**, a JSON list. The shell form (`ENTRYPOINT java -jar ...`) starts a shell and `java` becomes its child, so `docker stop` signals the shell, not Java, and the app is killed instead of shutting down cleanly. With the exec form Java is process 1 and receives the stop signal; with `server.shutdown=graceful` (new in `application.properties`) it finishes the requests in progress first, for at most 20 seconds.
- `-XX:MaxRAMPercentage=75` lets the JVM size its memory from the container's limit, not from the whole machine.

### `.dockerignore`
A file at the root of the context listing what must **not** be sent: `.git`, every `target` folder, the database files (`*.mv.db`), `.env` files (secrets!), logs. It makes the build faster and keeps private files out of the image.

### `compose.yaml`
```yaml
services:
  shop-api:
    build: { context: ../../.., dockerfile: lessons/45-docker/solution/Dockerfile }
    ports: ["8080:8080"]            # your PC:container
    environment:
      SHOP_DATA_DIR: /data
      SHOP_SECURITY_ADMIN_PASSWORD: ${SHOP_ADMIN_PASSWORD:-admin123}
    volumes: ["shop-data:/data"]
volumes:
  shop-data:
```
One command, `docker compose -f lessons/45-docker/solution/compose.yaml up --build`, builds the image and starts it. `${SHOP_ADMIN_PASSWORD:-admin123}` means "use the variable from the shell (or a `.env` file) if it exists, otherwise `admin123`". The default is for learning on your own PC only: **lesson 46 removes it**.

### What the tests can and cannot prove
`DockerFilesTest` checks things that matter and are visible in text: two stages, pinned tags, a JRE at runtime, a non-root `USER`, an exec-form `ENTRYPOINT`, the cache-friendly order, no password in the file, the volume, the port, secrets coming from the environment, and a useful `.dockerignore`. It cannot prove that the image builds, starts, or answers; only `docker build` and a `curl` can. Tests like these catch the mistakes people make most often; they do not replace trying it.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `COPY failed: file not found in build context` | The build was started from the wrong folder, or `.dockerignore` hides the file | Run `docker build` from the repository root, with `-f lessons/.../Dockerfile` and a final `.` |
| `exec ./mvnw: no such file or directory` or `bad interpreter` | `mvnw` has Windows line endings | The `sed -i 's/\r$//' mvnw` line fixes it in the image; add `mvnw text eol=lf` to `.gitattributes` for good |
| The build downloads every library on every build | `COPY . .` before the download, or the pom is copied after the source | Pom first, download, then source |
| `Could not find artifact ...parent` in the build | The root `pom.xml` was not copied | The context is the repository root; `COPY mvnw pom.xml ./` |
| The container exits at once | The app crashed at start-up | `docker logs <container>`; run without `-d` to see it |
| `Port 8080 is already allocated` | Something else (your local run of the app) uses 8080 | Stop it, or publish another port: `-p 9090:8080` |
| `curl: (52) Empty reply` right after `docker run` | The app is still starting (about 5 seconds) | Wait and retry (lesson 47 adds a proper readiness check) |
| The data is gone after `docker compose down -v` or after `docker run` without `-v` | The database lived inside the container's own disk | Use the volume; `down -v` deletes it on purpose |
| `Permission denied` writing `/data` | The folder belongs to root | `chown shop:shop /data` before `USER shop`, as in the Dockerfile |
| `docker stop` takes 10 seconds, then kills | The shell-form `ENTRYPOINT` swallowed the signal | Use the exec form |
| The image is huge | The runtime stage uses the JDK, or has the Maven cache | `eclipse-temurin:21-jre` and copy only the jar |
| A password is in `docker history` or in the image | It was written in the Dockerfile with `ENV` or `ARG` | Never. Pass secrets at run time (lesson 46) |
| Slow builds on Windows | Docker Desktop with the files on the Windows disk | Use WSL 2 and keep the project in the Linux file system, or accept the slower speed |

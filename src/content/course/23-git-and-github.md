## 1. Learning objectives
After this lesson you can:
- explain **working folder, staging area, repository, commit, branch, HEAD, remote** in your own words;
- use the daily loop: `git status`, `git add`, `git commit`, `git log --oneline --graph`, `git diff`, `git restore`;
- work the **GitHub flow**: branch, commit, push, pull request, review, merge, delete the branch;
- recognise the three conflict markers, resolve a **merge conflict** and finish the merge;
- write commit messages (`feat: ...`, `fix: ...`) and branch names (`feature/add-report`) that other people can read;
- undo a mistake safely, and know which Git commands can destroy work.

## 2. Plain-English explanation
- **Why Git?** Git remembers every version of your project, lets you try an idea without risking the working code, and lets many people work on the same files. Employers expect it. GitHub is a website that stores Git repositories and adds pull requests, reviews and automatic checks (CI).
- **Three places for your files.**
  1. The **working folder**: the files you see and edit.
  2. The **staging area** (the "index"): the files you have chosen for the *next* snapshot (`git add`).
  3. The **repository** (the hidden `.git` folder): the saved snapshots, called **commits** (`git commit`).
  Each commit has an id, your message, the author, the time and a pointer to the commit before it. That chain is the history.
- **Branch.** A movable label on a commit. `main` is the branch with the working, tested version. A new branch (`git switch -c feature/x`) lets you commit freely; when the work is good, you **merge** it back. `HEAD` is "the branch (and commit) you are on now".
- **Remote.** A copy of the repository somewhere else, usually on GitHub. It is named `origin` by default. `git push` sends your commits; `git fetch` downloads others' commits; `git pull` is fetch plus merge. A **fork** is your own GitHub copy of someone else's repository; a **clone** is a copy on your computer. With a fork you often add a second remote called `upstream` for the original.
- **The GitHub flow** (what almost every team does, in six steps):
  1. `main` is always working. Never commit straight to it.
  2. Make a **branch** with a descriptive name.
  3. Make **small commits** with clear messages.
  4. **Push** the branch and open a **pull request** (PR): "please review and merge this".
  5. **CI** (automatic checks, see `.github/workflows/ci.yml` in this repo) runs the tests; teammates review and comment. Fix and push more commits to the same branch.
  6. **Merge** the PR, delete the branch, update your local `main` (`git switch main`, `git pull`).
- **Commits worth reading.** One logical change per commit. Message form used in this course: `type: short summary` with the type one of `feat`, `fix`, `docs`, `test`, `refactor`, `chore`; the summary starts with a small letter, has no full stop, and the first line is at most 72 characters. Add a blank line and details if needed. Good: `fix: correct the sign of a sale total`. Bad: `changes`, `stuff`, `Fixed it.`
- **Pull requests worth reviewing.** Small (under a few hundred lines), one purpose, a title like a commit message, a description that says *what, why, how to check it*, and a green CI tick. Reviewers read the diff, ask questions, and approve. A PR is a conversation, not an exam.
- **Merge conflicts.** If two branches change the **same lines**, Git cannot know which to keep. It stops and writes both versions into the file:
  ```
  <<<<<<< HEAD                    <- your side (the branch you are on)
  4. Show stock report
  =======                         <- the divider
  4. Stock and reorder report
  >>>>>>> feature/reorder-report  <- the other branch
  ```
  To resolve: open the file, decide what the lines should say (often a mixture), **delete the three marker lines**, save, `git add file`, `git commit`. Run the tests. A conflict is not an error; it is Git asking a human to decide. Different lines or different files merge by themselves.
- **.gitignore.** Files that must not be committed: build output (`target/`), your IDE settings, saved data (`shop-data/`), and anything secret (passwords, keys, tokens). Once a secret is pushed, assume it is public: change it.
- **Undo, from safe to dangerous.**
  | You want to... | Command | Safe? |
  |---|---|---|
  | throw away edits to a file (not yet added) | `git restore file` | edits are gone for good |
  | un-add a file (keep the edits) | `git restore --staged file` | yes |
  | fix the last commit's message or add a forgotten file (not pushed yet) | `git commit --amend` | yes, if not pushed |
  | undo a commit that is already pushed | `git revert <id>` (makes a new commit that cancels it) | yes |
  | throw away everything uncommitted | `git reset --hard` | **destroys work** |
  | rewrite pushed history | `git push --force` | **never on shared branches** |
  Rule of thumb: before anything with `--hard` or `--force`, run `git status` and ask "is there anything here I cannot get back?".
- **Tags** mark a commit forever: `git tag milestone-4` then `git push origin milestone-4`. The course's milestones are tags.
- **`git bisect`** (a taste): when something that used to work is broken, Git can binary-search the history: you say `git bisect start`, `git bisect bad` (now), `git bisect good <old id>`, and for each step Git checks out a commit and you run the tests and answer good/bad. In about 10 steps it names the commit that broke it (lesson 22's "what changed since it worked?").
- **Using Git on Windows.** Use Git Bash or the terminal in your IDE. Set your name and e-mail once. Line endings: `git config --global core.autocrlf true` on Windows (so files are LF in the repository and CRLF on your disk), `input` on Mac/Linux.
- **Nothing new in the app's design this lesson.** The only code change is a small feature that you add *using the flow*: the stock report ends with a "To reorder:" section (from lesson 21's `ReorderAdvisor`).

## 4. Step-by-step: your first pull request
Do these in your **own fork** (so nothing here can harm anyone's repository).
1. **Fork and clone.** On GitHub press *Fork* on the course repository. Then, in a terminal where you keep projects (`C:\projects` on Windows):
   ```
   git clone https://github.com/<your-user-name>/java-by-building.git
   cd java-by-building
   git remote -v            # origin = your fork
   git remote add upstream https://github.com/<original-owner>/java-by-building.git
   ```
2. **Check your Git setup.** `git --version`, then `git config user.name` and `git config user.email` must print your details (set them with `git config --global user.name "Your Name"` if not).
3. **Branch.** `git switch -c feature/reorder-in-report`, then `git branch --show-current` prints it. Never work on `main`.
4. **See the red.** In `lessons/23-git-and-github/starter` run `../../../mvnw test`. Two tests in `MenuTest` fail (`stockReportEndsWithWhatToReorder` and `whenEverythingIsStockedTheReportSaysThereIsNothingToReorder`); everything else passes.
5. **Make the change.** In `Menu.showReport` follow the TODO: after the "Sales so far" line print an empty line, `To reorder:` and the report from `ReorderAdvisor`. Run the tests until green.
6. **Review your own change before committing.** `git status` (what changed?), `git diff` (exactly what?). Only `Menu.java` should be listed. If `target/` or other files show up, stop: they belong in `.gitignore`.
7. **Commit.** `git add lessons/23-git-and-github/starter/src/main/java/dev/javabybuilding/inventory/Menu.java`, then
   `git commit -m "feat: show reorder suggestions in the stock report"`. Check the message with the rules in section 2 (the exercise `CommitMessages` checks the same rules). `git log --oneline -3` shows it.
8. **Push and open the PR.** `git push -u origin feature/reorder-in-report`. GitHub prints a link, or press *Compare & pull request*. Set the base to **your fork's `main`**. Write the title like the commit message, and in the description say what changed, why, and "ran `./mvnw test` in lessons/23-git-and-github/starter: green". Wait for the CI tick. Copy the PR's address, you need it for the checkpoint.
9. **Review.** Read your own PR's *Files changed* tab as a reviewer would. Add one comment on a line (good practice even if you agree).
10. **Practise a conflict.** Do this by hand in a scratch folder outside the repository (the `%TEMP%` folder works). It is the same story as `GitSandbox.java`:
    ```
    mkdir conflict-practice && cd conflict-practice
    git init -b main
    # create menu.txt with five lines (1. Add product ... 5. Quit), then:
    git add menu.txt && git commit -m "feat: add the menu"
    git switch -c feature/reorder-report
    # change line 4 to "4. Stock and reorder report", then:
    git commit -am "feat: show reorder suggestions in the report"
    git switch main
    # change line 4 to "4. Show stock report", then:
    git commit -am "fix: clearer wording for the report choice"
    git merge feature/reorder-report       # CONFLICT
    git status                             # menu.txt is "both modified"
    ```
    Open `menu.txt`, make line 4 say `4. Show stock and reorder report`, delete the three marker lines, then `git add menu.txt` and `git commit` (accept the message). `git log --oneline --graph` shows the two lines of work joined.
11. **Resolve the practice file in the repo.** In `lessons/23-git-and-github/exercises/practice/menu-notes.txt` someone has already left conflict markers in. Resolve it the same way (keep **both** ideas on line 4), on a branch, and commit.
12. **Write your checkpoint.** In `lessons/23-git-and-github/exercises` copy `my-checkpoint.example.txt` to `my-checkpoint.txt` and fill in your name, GitHub user name, branch, commit message, PR address and `conflict-resolved: yes`. Commit it on your branch.
13. **Merge your PR** on GitHub (button *Merge pull request*), delete the branch, then `git switch main` and `git pull`. `git log --oneline --graph -5` shows your work in `main`.
14. **Tag a milestone** (optional, recommended): `git tag milestone-4` on the lesson 20 commit or on your `main`, then `git push origin milestone-4`.

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `fatal: not a git repository` | You are not inside the cloned folder | `cd` into the repository folder |
| `Please tell me who you are` | Name and e-mail not set | `git config --global user.name "..."` and `user.email` |
| `nothing added to commit but untracked files present` | You forgot `git add` | `git add <file>` then commit |
| `error: failed to push some refs ... (fetch first)` | The remote has commits you do not have | `git pull`, resolve any conflict, push again. Never `--force` to get past it |
| `You have unmerged paths` / `CONFLICT` | A merge hit the same lines | Edit the file, remove the three marker lines, `git add`, `git commit` |
| You committed with markers still in the file (`<<<<<<<`) | Resolved in a hurry | Edit, `git commit -am "fix: remove conflict markers"`; the build will tell you |
| You committed on `main` by mistake (not pushed yet) | Forgot to branch | `git branch feature/x` (keeps the commit), then `git reset --hard origin/main` on main. Ask before using `--hard` |
| `target/` shows up in `git status` | Not in `.gitignore` | It is already ignored here; if you made your own repository, add `target/` |
| Windows: `warning: LF will be replaced by CRLF` | Line-ending conversion | Normal with `core.autocrlf true`; not a problem |
| The PR shows 40 changed files you did not touch | Wrong base branch, or you committed build output | Check the base is your fork's `main`; remove the extra files from the commit |
| You pushed a password or token | A secret is in the history | Treat it as public: change the password / revoke the token **now**, then ask for help cleaning history |

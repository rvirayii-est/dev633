## 2. Plain-English explanation
Once the app runs on a server nobody is watching it. Three tools tell you what is going on:

| Tool | Question | Example |
|---|---|---|
| **Health check** | Is it working *right now*? | `GET /actuator/health` answers `UP` or `DOWN` |
| **Metrics** | How is it doing, as numbers over time? | requests per second, slow requests, memory, database connections |
| **Logs** | What happened, in order? | `GET /products/salt -> 404 in 57 ms` |

A platform (Docker, Kubernetes, a hosting service, a load balancer) calls the health check every few seconds and acts on the answer. People use metrics to see trends and logs to find out *why*.

### Spring Boot Actuator
One dependency, `spring-boot-starter-actuator`, adds ready-made endpoints under `/actuator`. It also brings **Micrometer**, the library that collects the metrics (you meet its names in `/actuator/metrics`).

**Expose only what you need.** Actuator has endpoints that are dangerous in the wrong hands: `env` (your settings), `beans`, `mappings`, `threaddump`, `heapdump` (a copy of the memory, with passwords in it), `shutdown`. By default only `health` is on the web. We switch on exactly three:
```properties
management.endpoints.web.exposure.include=health,info,metrics
```
`ActuatorTest.dangerousEndpointsAreNotExposedEvenToAnAdmin` proves `env`, `beans`, `heapdump`, `threaddump`, `mappings`, `configprops` and `shutdown` answer `404`. (The starter has `include=*`, a very common mistake; TODO 3 fixes it.)

### Who may see what
| Path | Stranger | Cashier | Admin |
|---|---|---|---|
| `/actuator/health`, `/health/liveness`, `/health/readiness` | `200` verdict only | `200` verdict only | `200` with the parts |
| `/actuator/info`, `/actuator/metrics/...`, `/actuator` | `401` | `403` | `200` |
Health must be public: a platform has no password. But the *details* (the database product, free disk space, the folder path) help an attacker, so `management.endpoint.health.show-details=when-authorized` and `...roles=ADMIN` show them to admins only. Notice that the admin's answer in section 6 contains the full path of the disk: another reason details are not for strangers.

### Liveness and readiness
They are two different questions, and mixing them up causes outages:
- **Liveness** ("is the process itself broken?"): if no, the platform **restarts** the app. Keep it simple. If liveness checked the database and the database went down, the platform would restart your perfectly healthy app in a loop, which does not mend the database.
- **Readiness** ("can it take requests now?"): if no, the platform **stops sending traffic** (and keeps the app). It is `DOWN` while starting up (loading, migrating, seeding) and when a dependency is down. We include the database: `management.endpoint.health.group.readiness.include=readinessState,db`.

Spring Boot turns readiness `UP` only after start-up has finished, including the code that seeds the sample products and the users. (In lesson 42 you may have met a `401` in the very first second: the seeder had not run yet. A platform that waits for readiness never sends that first request.) `HealthAggregator.java` plays the four situations: normal, starting, database down, deadlocked.

### Logs: three habits
1. **A request id.** `RequestIdFilter` gives each request an id (or reuses a plain one from the caller's `X-Request-Id` header), puts it in the **MDC** (a per-thread map the logger reads), returns it in the response header, and writes one line when the request ends: `GET /products/salt -> 404 in 57 ms`. When a customer says "my sale failed", the id on the response finds *every* log line of that request.
   - The incoming id is user input. An id with a newline could forge a log line (`abc\nINFO fake`), so only 1 to 64 plain characters are accepted; anything else is replaced.
   - The filter runs **first** (before Spring Security), so even a refused request gets an id and a log line.
   - The MDC is cleaned in a `finally`: server threads are reused, and a left-over id would label the next request wrongly.
2. **The id in every line.** `logging.pattern.level=%5p [%X{requestId:-}]` prints it in the human format.
3. **Structured logs in production.** In the `prod` profile `logging.structured.format.console=logstash` makes Spring Boot (3.4 and later) print one JSON object per line instead of text. A log collector can then search `requestId`, `level` and `message` as fields instead of guessing with patterns. (The drill `toJsonLine` writes one by hand; do not do that in real code: escaping is exactly where hand-made JSON goes wrong.)

**Never log:** passwords, tokens, full card numbers, the `Authorization` header. The filter logs the method, the path, the status and the time, and nothing from the body or the headers.

### Metrics: use percentiles, not averages
`/actuator/metrics/http.server.requests` counts requests, total time and slowest. An **average** hides trouble: 95 requests at 10 ms and 5 at 2000 ms have an average of 109.5 ms and nobody was served in 109 ms. The **95th percentile** ("95 of 100 requests were at least this fast") says 10 ms, and the 96th says 2000 ms. Exercise 6 computes it. (Prometheus and Grafana, the usual tools to collect and draw metrics over time, are the next step; they read the same Micrometer data.)

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `/actuator/health` answers `401` | The health rule is missing, or below the catch-all | `permitAll()` for `/actuator/health` and `/actuator/health/**`, above `.anyRequest()` |
| `/actuator/metrics` answers `404` in your own test | Spring Boot turns metrics off in tests | `@AutoConfigureObservability` on the test class |
| `/actuator/env` answers `200` | `management.endpoints.web.exposure.include=*` | List the endpoints you need. Never `*` on a server |
| The admin sees no `components` | The password was not sent, or the user is not an admin | `management.endpoint.health.roles=ADMIN` and `-u admin:...` |
| Everyone sees `components` | `show-details=always` | `when-authorized` |
| The platform restarts the app again and again | Liveness checks something outside the process (the database) | Liveness = the process only; put dependencies in readiness |
| The id is missing in log lines of another thread | The MDC belongs to one thread; work handed to another thread does not carry it | Copy the MDC when you start a thread, or use a library that does |
| The id of the previous request shows up | The MDC was not cleaned | `MDC.remove(...)` in `finally` |
| `No qualifying bean of type RequestMappingHandlerMapping ... found 2` | The actuator adds a second mapping | Inject by name: `@Qualifier("requestMappingHandlerMapping")` |
| Log lines are plain text in production | The `prod` profile is not active | `SPRING_PROFILES_ACTIVE=prod` |
| Logs show a password | Someone logged a request body or a header | Review every `LOG.` call; log ids and counts, not payloads |
| Health says `UP` but the app is useless | The check does not look at what matters | Add a custom `HealthIndicator` for a real dependency (a stretch idea; keep it quick and without side effects) |

## 1. Learning objectives
After this lesson you can:
- **choose** the cheapest kind of test that can catch a given bug: plain JUnit, a *slice* (`@WebMvcTest`, `@DataJpaTest`) or the *whole application* (`@SpringBootTest`);
- **send** a request with `MockMvc` and **check** the status, the `Location` header and the JSON with `jsonPath`;
- **fake** a service with `@MockitoBean`, teach it answers with `when(...).thenReturn/thenThrow`, and check calls with `verify`;
- **write** a scenario test: create, receive, sell, report, delete, through every real layer, with no network;
- **finish Milestone M6**: a REST API for the Inventory & Sales System, fully tested, that you can run, call and trust.

## 2. Plain-English explanation
You have been testing since lesson 21, and the API already has tests (look at lessons 36-39). This lesson makes the *method* explicit, because an API has many more ways to break than a console program: a wrong URL, a missing header, a field spelled wrong, a status code off by one, an error that leaks. The only safe way to change an API later is to have tests that say what it promises.

### The test pyramid (three sizes of test)
```
        /\          few    full tests      @SpringBootTest        everything real, slowest (about 2 s to start)
       /  \
      /----\        some   slice tests     @WebMvcTest            only the web layer, fakes behind it (fast)
     /      \                              @DataJpaTest           only the database layer (fast)
    /--------\      many   plain tests     JUnit, no Spring       one class at a time (instant)
```
Rule of thumb: **test each thing at the smallest size that can show the bug.** Many fast tests at the bottom, a few slow ones at the top. If every test starts the whole application, the suite takes minutes, and developers stop running it.

| Question | Smallest test that answers it | In this project |
|---|---|---|
| Is the price rule right? A sale takes stock off? | plain JUnit on `ShopService` | lessons 21, 30, 31 |
| Does the service build the right customer and discount? | plain JUnit on `SaleService` | `SaleAndReportServiceTest` |
| Is a field rule right (`quantity` of 0)? | plain `Validator` | `ValidationTest` |
| Does the error handler hide a bug's details? | plain call with a fake request | `ApiExceptionHandlerTest` |
| Does the JPA mapping match the tables? Same results as the in-memory repository? | `@DataJpaTest` | `JpaRepositoriesTest` (lesson 38) |
| Is the URL, status code, header, JSON shape right? Is a bad body refused *before* the service? | **`@WebMvcTest` + MockMvc** | `ProductControllerWebTest`, `SaleControllerWebTest` |
| Do all the layers work together? | `@SpringBootTest` + MockMvc | `ShopScenarioMockMvcTest`, `ApiErrorsMockMvcTest` |
| Does the packaged app answer on a real port? | `@SpringBootTest(RANDOM_PORT)` + `HttpClient` | `ServerSmokeTest` (2 tests) |

### MockMvc: a web server that is only a function
A web app is, at heart, a function: a request goes in, a response comes out. A real server wraps it in sockets and threads. **MockMvc** skips the wrapping: it builds the request object, hands it to Spring's front controller in the same JVM, and gives the response back. Same code runs (routing, JSON conversion, validation, your error handler), but there is no port, no Tomcat, nothing to start or stop. `DirectVsHttp.java` (examples) shows the idea in 70 lines: the same four checks run directly and over real HTTP and agree.

```java
mvc.perform(get("/products/{name}", "Rice 25kg"))              // send the request
   .andExpect(status().isOk())                                   // check the status
   .andExpect(header().string("Location", "/products/Salt%201kg"))   // check a header
   .andExpect(jsonPath("$.name").value("Rice 25kg"))             // check a field of the JSON answer
   .andExpect(jsonPath("$.problems[0].field").value("price"))    // arrays: [0]
   .andExpect(jsonPath("$.length()").value(4))                   // functions: length()
   .andExpect(content().json("{...}", true));                    // the whole body; true = strict (nothing extra, same order)
```
- `get`, `post`, `put`, `delete` build the request. `.contentType(MediaType.APPLICATION_JSON).content("{...}")` adds a JSON body. `.param("status", "low")` adds `?status=low`. `get("/products/{name}", "Rice 25kg")` fills a variable and URL-encodes it.
- `jsonPath` takes a path into the JSON answer (`$` is the root, `.name` a field, `[0]` an item). `ProductControllerWebTest` uses `$.problems[?(@.field == 'price')].message` to find an item by a field. Exercise 1 writes the small version.
- `andDo(print())` prints the whole request and response: the first thing to try when a test surprises you (output in section 6).

### Slice tests and fakes: `@WebMvcTest` and `@MockitoBean`
```java
@WebMvcTest(ProductController.class)       // start ONLY the web layer, with this controller (and the error advice, Jackson, validation)
class ProductControllerWebTest {
    @Autowired MockMvc mvc;                // Spring makes the MockMvc
    @MockitoBean ProductService products;  // a fake service: Mockito makes it, Spring puts it where the controller wants a real one
```
The controller's constructor asks for a `ProductService` (lesson 36's dependency injection). In a slice there is no real service, so `@MockitoBean` supplies a fake that does nothing until you teach it:
- `when(products.get("salt")).thenThrow(new UnknownProductException("salt"));` — "when asked for salt, throw this";
- `when(products.list(null)).thenReturn(List.of(...));` — "when asked for everything, answer this";
- `verify(products).update("Rice 25kg", new UpdateProductRequest(...));` — "it must have been called, with exactly these arguments" (records have `equals`, so this works);
- `verifyNoInteractions(products);` — "it must NOT have been called": the proof that a bad request is stopped at the door.

Why the fake? The slice test is about the **web layer**: URLs, methods, JSON, status codes, validation. With the service faked, a failing test can only be a web-layer bug. The shop's rules have their own tests; testing them again here would be slow and repeat work.

### The full scenario: `@SpringBootTest` + `@AutoConfigureMockMvc`
`ShopScenarioMockMvcTest` starts the real application (controllers, services, the shop core, JPA, Flyway, an in-memory H2) and still uses MockMvc, so there is no port. The tests run in order (`@Order`) and tell one story: the shop opens with four products; a product is created and received; it is changed; a sale is made and shows up in both reports; a sale that cannot happen changes nothing; only a product with no history can be deleted. This is the **acceptance test of Milestone M6**.

Because the whole application is real, these tests share state, so the order is part of the test. That is acceptable for **one** scenario. Everywhere else, tests must be independent.

### Fast, repeatable, and clean
A test suite you cannot trust is worse than none. This project follows five habits:
1. **Deterministic answers.** No `timestamp` in an error (it would change every run); problems come back sorted; the clock is fixed in service tests (`TestShop.CLOCK`).
2. **No leftovers.** In-memory databases with their own names (`jdbc:h2:mem:mvc-it`), `@TempDir` for the one test that needs a file. `git status` is clean after the build.
3. **Few slow tests.** Spring starts an application once per *distinct configuration* and **reuses it** for every test class with the same settings. `ShopScenarioMockMvcTest`, `ApiErrorsMockMvcTest` and `ApiDesignMappingTest` use identical annotations on purpose: one start-up, three classes. Adding a `@MockitoBean` or a different property to one test class makes Spring start a new application for it.
4. **Random ports, never fixed ones.** `ServerSmokeTest` uses `RANDOM_PORT`; a test that needs 8080 fails when anything else is running.
5. **One reason to fail.** Name tests after what they promise (`anEmptyBodyIs400WithEveryRequiredFieldNamed...`), arrange-act-assert, and check one idea per test.

### The design table keeps the code honest
`ApiDesignMappingTest` asks Spring which `(method, path)` pairs the controllers really map and compares them with `ApiDesign.ENDPOINTS`, the table of lesson 34. Add an endpoint and forget the table, and the build fails. (In lesson 34 the plain-Java `ShopApi` had the same check.)

## 7. Common mistakes and troubleshooting
| Symptom | Cause | Fix |
|---|---|---|
| `No qualifying bean of type 'ProductService'` in a `@WebMvcTest` | The slice does not load services | Add `@MockitoBean ProductService products;` |
| Two `when(mock.method(...)).thenThrow(...)` lines: the second throws at once | `when(mock.method())` **calls** the method, which the first stub already makes throw | Re-stub with `doThrow(...).when(mock).method(...)` |
| `Status expected:<200> but was:<415>` | No `.contentType(MediaType.APPLICATION_JSON)` on a request with a body | Add it (the `json(...)` helper does) |
| `Status expected:<201> but was:<400>` | The JSON body breaks a rule (see the `problems` in the output) | `andDo(print())` and read the body |
| `JSON path "$.price" expected:<1250.50> but was:<1250.5>` | `jsonPath` hands you a number (a `Double` or an `Integer`), and you compared it with text | Compare with a number: `value(1250.50)`; to check the exact text of the body use `content().string(...)` |
| `jsonPath(...).value(...)` fails with `No value at JSON path` | The field is missing, or the path has a typo | Print the body and count the levels |
| Tests pass alone but fail together | Shared state: one in-memory database, tests that change it, an order assumption | Give each test class its own database name, or make the tests independent; if you need a story, use `@Order` and keep it in ONE class |
| Spring starts a new application for every test class (slow) | Each class has different settings or its own `@MockitoBean` | Use the same annotations and properties, or accept that a slice is cheap and a full test is not |
| `Address already in use` in a test | A test used a fixed port | `RANDOM_PORT` |
| Deprecated `@MockBean` | Older Spring Boot style | `@MockitoBean` (`org.springframework.test.context.bean.override.mockito`) |
| `A Java agent has been loaded dynamically` printed on Java 21 | Mockito attaches an agent | The pom's `argLine` `-XX:+EnableDynamicAgentLoading` allows it on purpose |
| A test leaves `shop-data` behind | It used the real file database | Use `jdbc:h2:mem:...` or `@TempDir`; run `git status` after the build |
